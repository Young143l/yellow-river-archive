# 数据规范

> 这份文档回答一个问题：**写到什么程度算合格**。
> 清单与进度看 [packages/data/sites.yaml](../packages/data/sites.yaml)；技术方案看 [设计文档](./设计文档.md)。
>
> 适用对象：所有参与档案撰写、校对、图片采集的人。

---

## 1. 数据集边界

### 1.1 只收「地点型」文化遗产

一处遗产 = 一个条目 = 一个 YAML 文件。只收地点型（遗址、城址、窑址、墓葬群、古建筑、石窟寺、碑刻、祭祀址、关隘、仓储、道路、河道）。

**不收**：单体文物、非遗、人物、诗词作为独立条目 —— 它们作为条目内的字段存在（`artifacts` / `figures` / `poems`）。

例外：文物虽不单独建条目，但**可被用户单独收藏**（见设计文档 §7.1）。

### 1.2 时代轴与「宋以后」

赛题给定的时代轴是六段：**仰韶 → 龙山 → 夏商 → 周 → 汉唐 → 宋**。

元明清遗存归入 **`宋以后`** 延伸分组，UI 上弱化展示。

**时代归类规则**：对于「始建于某朝、现存建筑为后世重建」的遗产（如开封大相国寺、洛阳关林），**时代按文化主体归类**，并在 `notes` 或正文中写明始建与现存建筑的年代差异。

> 现状提醒：当前 80 条中 `宋以后` 有 19 条（24%），偏多。撰写正文时若发现某条其实有更早的文化主体（如始建于唐宋），应改归入对应时代并在 `notes` 说明。

### 1.3 城市与配额

| 城市 | 配额 | 说明 |
|---|---|---|
| 洛阳 | 20 | 世界遗产 + 大量国保，资源最丰 |
| 郑州 | 20 | 含登封「天地之中」系列 + 巩义窑址群 |
| 开封 | 16 | 北宋都城系列 |
| 三门峡 | 14 | 仰韶文化核心区 + 虢国墓地 |
| 濮阳 | 10 | 国保数量有限，不强行凑数 |

### 1.4 类型覆盖硬要求

赛题点名的四类 —— **都城遗址 / 墓葬群 / 窑址 / 古建筑** —— 每类**不得少于 6 条**。

这条由 `pnpm data:sites` 自动体检，不足会报错。

## 2. 条目字段定义

字段的机器约束由 [packages/shared/src/schemas.ts](../packages/shared/src/schemas.ts) 定义，写入时会被校验。

| 字段 | 必填 | 约束 | 说明与常见错误 |
|---|---|---|---|
| `id` | 是 | `^[a-z]{2,3}-[a-z0-9-]+$` | 城市前缀 + 拼音，如 `ly-erlitou`。**一经确定不改**，它是路由、外键与图片命名的基准 |
| `name` | 是 | 非空 | 用遗产的通用名称 |
| `aliases` | 是 | 数组，可为空 | 别名与俗称，如 `['铁塔', '开封铁塔']`，用于检索命中 |
| `city` | 是 | 枚举 5 城 | 按现行行政区划 |
| `era` | 是 | 枚举 7 值 | 见 §1.2 归类规则 |
| `eraRange` | 否 | `[起始年, 结束年]` | 负数表示公元前。例：`[-1750, -1530]`。**拿不准就留空**，不要编 |
| `types` | 是 | 至少 1 个 | 见类型枚举；一处遗产可属多类 |
| `level` | 否 | 枚举 | 世界遗产 / 全国重点文保 / 省级文保 / 市县级文保 / 未定级 |
| `batch` | 否 | 数字 | 国保批次（第一批 ~ 第八批），写在清单里 |
| `geo` | 是 | lat [-90,90] / lng [-180,180] | 遗址中心点坐标，保留 4 位小数即可 |
| `summary` | 是 | **10-120 字** | 一句话概述，会成为卡片副标题与检索片段首条 |
| `intro` | 是 | **200-1200 字** | 图文介绍，见 §3.1 |
| `archaeology` | 是 | **150-900 字** | 考古发现，见 §3.2 |
| `events` | 是 | 数组，可为空 | 历史事件，见 §3.3 |
| `poems` | 是 | 数组，可为空 | 相关诗词，见 §3.4 |
| `travel` | 否 | 对象 | 文旅信息，见 §3.5 |
| `artifacts` | 是 | 数组，可为空 | 出土文物，`id` 格式 `<itemId>#<序号>` |
| `figures` | 是 | 数组，可为空 | 相关人物 |
| `images` | 是 | **至少 1 条** | 每条的 `credit` 与 `license` **均不得为空** |
| `keywords` | 是 | **至少 3 个** | 检索关键词，含专名、别名、文化标签 |
| `sources` | 是 | **至少 1 条** | 来源必须可访问，`accessedAt` 为 ISO 日期 |

## 3. 五层内容撰写标准

### 3.1 图文介绍（`intro`，300-800 字为准）

**写什么**：地理位置与范围、年代与分期、在文化序列中的位置、最值得记住的一点。

**结构建议**（三段）：
1. 在哪里、什么年代、体量多大
2. 有什么（布局、遗迹、遗物）—— 挑最有代表性的讲
3. 意味着什么（学术价值、历史意义）

**禁忌**：不写「欢迎参观」「值得一游」这类旅游软文语气；不堆砌形容词；不出现「本文」「综上所述」等论文腔。

### 3.2 考古发现（`archaeology`，200-600 字）

**必须包含**：发现时间、发现者或发掘单位、关键遗物、学术意义。

有争议的结论一律用**「学界多认为」「一般认为」**表述，不要写死。年代用「约」。

### 3.3 历史事件（`events`，2-5 条）

每条三个字段：

| 字段 | 格式 | 示例 |
|---|---|---|
| `year` | 年份字符串，可含朝代 | `'1959'`、`'公元前 1750 年'` |
| `title` | 8 字以内 | `遗址被发现` |
| `desc` | 一句话说清「谁做了什么、结果如何」 | `徐旭生率队在豫西进行夏墟调查时发现二里头遗址。` |

**挑选原则**：优先「发现 / 定名 / 列入国保 / 重要发掘或保护节点」，不要写无关的地方志事件。

### 3.4 相关诗词（`poems`，0-3 首）

**引擎里的排序意味着**：能引直引就直引，不能就留空。

| 情形 | 处理 |
|---|---|
| 有直接关联的诗词 | 直引原文，`note` 可留空或注释背景 |
| 无直接关联（如二里头，古代未知其存在） | **留空数组**，不要硬凑 |
| 只有同城 / 同题材诗词 | 可以引，但**必须在 `note` 里写明**「该诗并非本遗址直接关联，取自同城题材」 |

**禁止**：托名伪作、来源不明的诗句、把现代人写的打油诗当古诗。

### 3.5 文旅信息（`travel`）与文物、人物

- `travel`：**拿不到就留空字段**，不要写「免费」「详情请咨询」。四个子字段：`hours` / `ticket` / `best` / `tips`
- `artifacts`：2-5 件，`desc` 一句话讲清「是什么、为什么重要」，能查到馆藏地就填 `museum`
- `figures`：1-3 位，优先与该遗产的发现、研究、保护直接相关的人

## 4. 来源策略与合规红线

### 4.1 可用来源（白名单）

- 中国大百科全书（考古学 / 文物卷）
- 国家文物局与省市文物局公开资料、全国重点文物保护单位名录
- 各遗址博物馆官网与官方公众号
- 地方志、公开出版的考古报告与学术论文
- 各地政府网站的文旅公开信息

### 4.2 禁止来源

- 商业旅游网站与自媒体文章（含公众号洗稿）
- 无出处的百科条目（**百度百科只能用来定位线索，不能作为正文来源**）
- 论坛、贴吧、问答平台
- 任何标注「版权所有、禁止转载」且未获授权的材料

### 4.3 改写红线（会取消资格的）

> 赛题原文：「参赛作品须由参赛学生独立完成，**严禁抄袭、剽窃**」。

**硬指标**：与来源原文**连续重合不超过 15 字**。

**改写手法**：
- 句式重组：主被动互换、长句拆分、从句前置
- 信息重排：按自己的逻辑顺序组织，不照抄原文顺序
- 术语替换：能用同义表述就用（但**专名与年代数字不得改**）
- 加入自己的整合：把多个来源的信息交叉印证后重新表述

**质检**：`pnpm data:lint` 会做 n-gram 查重，超阈值直接报错。

### 4.4 事实表述规范

| 情形 | 写法 |
|---|---|
| 学术争议 | 「学界多认为」「一般认为」「存在争议」 |
| 年代不确定 | 「约」「距今约」 |
| 传说性内容 | 写明「相传」「传为」，不要让读者误以为是史实 |
| 未定论 | 不写死，或直接不写 |

## 5. 图片规范

| 项 | 要求 |
|---|---|
| 数量 | 每条**主图 1 张必配**，补充图 0-3 张 |
| 格式 | WebP |
| 尺寸 | 长边 ≤1080px，另出 200px 缩略图 |
| 单张体积 | 80-150KB |
| 命名 | `<itemId>-<序号>.webp`，存放于 `assets/img/` |
| 版权 | `credit`（作者或来源）与 `license`（授权协议）**均不得为空** |
| 允许来源 | Wikimedia Commons（若有国际源可用）、官方公开渠道、**自绘示意图** |

**责任分工**：主图跟随撰写人（谁写谁找），补充图由图片负责人统一补，版权台账由图片负责人总审。

**占位图规则**：撰写阶段可用占位图，但必须在 `caption` 里写明「占位图」，且 **P0 批次提交前必须替换为真图或自绘示意图**。

## 6. 生产流程

```
① 来源摘录      packages/data/sources/<id>.md
                整理 3-5 个来源的关键段落 + 出处 URL
                      ↓
② AI 起草       tools/pipeline/draft.ts（调 DeepSeek）
                硬约束：不得编造年代与数字；不确定处标 [待核实]；事实句标来源编号
                输出：packages/data/drafts/<id>.yaml（草稿，禁止直接入库）
                      ↓
③ 人工改写      owner 在编辑器里改
                重点：去 AI 腔、句式重组、事实核对、补充本地细节
                输出：packages/data/sites/<id>.yaml
                      ↓
④ 交叉校对      reviewer（不得与 owner 同人）
                重点：事实错误、表述规范、字段完整性
                      ↓
⑤ 自动质检      tools/pipeline/lint.ts
                schema / 字数 / license / 分布 / n-gram 查重
                      ↓
⑥ 入库         pnpm data:build
                生成端侧预置包
```

**为什么要有「来源摘录」这一步**：它同时解决三件事 —— AI 有据可依不会瞎编、改写时知道原文长什么样、`sources` 字段自动有据可填。

## 7. 分工与进度

### 7.1 分工方式

- **首批（P0 的 20 条）**：三人均分，各领 6-7 条，**跨城市**。目的是先用小批量跑通流程、暴露问题
- **之后（P1 / P2）**：按城市包干（每人 1-2 城），减少沟通成本

### 7.2 责任字段

`sites.yaml` 里每条都有 `owner` 与 `reviewer`，规则：

1. **owner 不得为自己校对**
2. 校对通过后由 owner 把 `status` 改为 `已核`
3. 发现矛盾无法裁决时改为 `存疑`，在看板上提出

### 7.3 进度查看

```bash
pnpm data:sites     # 清单体检：条目数、配额、类型覆盖、P0 门禁、正文进度
pnpm data:status    # 正文数据分布与校验
pnpm data:build     # 重新生成端侧预置包
```

## 8. 核对流程

### 8.1 为什么要人工核对

Agent 已实测：Wikidata 与维基百科不可达，百度百科需验证码，中国大百科全书与国家文物局均为 JS 动态渲染 —— **自动抓取不可行**（详见 [ADR-022](./decisions.md)）。

因此采用**双轨制**：Agent 产出带置信度的初稿，**人工用浏览器逐项核对**。

### 8.2 核对什么

每条至少核对这五项：

| 项 | 核对要点 |
|---|---|
| 城市归属 | 按现行行政区划（注意县级市归属，如巩义属郑州、义马属三门峡） |
| 时代 | 是否与 `era` 枚举一致；「宋以后」是否其实可归入更早时代 |
| 类型 | 是否覆盖了赛题四类中的某一类 |
| 文保级别与批次 | 世界遗产 / 国保第几批 / 省级 |
| 坐标 | 与实际位置偏差是否在合理范围（同城即可，不必精确到米） |

### 8.3 核对后要改什么

1. 更新 `status`（`已核`）
2. 修正有误的字段
3. 修正 `confidence`（`low` → `medium` → `high`）
4. 把可访问的来源链接补进正文的 `sources`

## 9. 自动质检规则

`pnpm data:lint` 会拦截以下问题：

| 检查 | 规则 | 拦截的后果 |
|---|---|---|
| Schema | Zod 逐字段校验 | 结构错误导致 App 崩溃 |
| 字数 | `intro` 200-1200、`archaeology` 150-900、`summary` 10-120 | 内容过薄或注水 |
| **n-gram 查重** | 与来源文本连续重合 ≥15 字即报错 | **抄袭风险（赛题取消资格）** |
| License 非空 | 每张图的 `credit` 与 `license` 必填 | 版权风险 |
| 类型覆盖 | 四类必填每类 ≥6 条 | 赛题点名类型缺失 |
| 时代覆盖 | 六个主时代每段 ≥8 条 | 时间轴出现空洞 |
| 城市覆盖 | 每城 ≥8 条 | 地图视图某城为空 |
| 占位图 | P0 批次不得含占位图 | 提交质量 |

## 10. 附录：字段速查卡

```
id            城市前缀-拼音           ly-erlitou
name          遗产名称                二里头遗址
aliases       别名数组                [偃师二里头]
city          五城之一                洛阳
era           七时代之一              夏商
eraRange      [起, 止]，负数=公元前   [-1750, -1530]
types         类型数组（≥1）          [都城遗址]
level         保护级别                全国重点文保
geo           {lat, lng}              34.6983, 112.7836
summary       10-120 字               学界多认为是夏代晚期都邑所在……
intro         200-1200 字             三段：在哪·有什么·意味着什么
archaeology   150-900 字              发现时间·发现者·关键遗物·学术意义
events        [{year,title,desc}]     1959 / 遗址被发现 / 徐旭生率队……
poems         [{title,author,dynasty,content,note?}]   无直接关联就留空
travel        {hours,ticket,best,tips}                拿不到就留空
artifacts     [{id,name,desc,museum?}]                 id = <itemId>#<序号>
figures       [{name,role,desc}]
images        [{url,caption,credit,license}]           credit/license 不得为空
keywords      ≥3 个                    [夏代都邑, 绿松石龙形器, 宫城]
sources       ≥1 条，必须可访问         [{title,url,accessedAt}]
```

**三条最容易踩的线**：连续 15 字重合（抄袭）、图片 license 为空（版权）、image 少于 1 张（schema 不过）。
