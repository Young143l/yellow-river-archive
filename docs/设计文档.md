## 1. 作品概述

### 1.1 一句话定位

**一条长在黄河时间轴上的个人知识库**：用户沿仰韶到宋的时代轴探索河南段黄河文化遗产，收藏、记笔记、打标签，系统据此自动生长出一张属于他自己的文化知识网络，并在多设备之间无缝同步。

### 1.2 目标用户与场景

| 用户 | 场景 | 我们的满足点 |
|---|---|---|
| 对黄河文化好奇的大学生 | 想搞懂"家门口这个遗址是什么" | 时间轴 + 三维筛选 + 五层详情 + AI 追问 |
| 周末出游的游客 | 想去洛阳看两天 | 城市视图 + 文旅信息 + 「待实地探访」标签 |
| 备课的历史老师 / 写论文的学生 | 长期积累资料 | 笔记 + 主题 + 知识网络 + 多设备同步 + 一键备份 |

### 1.3 三个记忆点（答辩主线）

1. **会生长的知识网络**：不是静态百科，收藏与笔记会自己长成主题簇（标签传播算法）
2. **两条腿的检索**：关键词精确命中专名 + 语义召回同义表达，断网时自动降级为单腿仍可用
3. **看得见的数据流转**：双通道同步 + 冲突可视化面板，把"分布式数据管理"从概念变成肉眼可见的东西

### 1.4 整体形态

- **端侧**：OpenHarmony（ArkTS，API 12+）手机 / 平板应用，全部内容离线预置
- **云侧**：自建 TS 服务，只承担两件事——**个人数据云存储**（同步中转 + 备份快照）与 **RAG 检索问答服务**（语义检索 + 图谱增强问答）。不掌管档案内容，不参与基础功能闭环

### 1.5 设计原则

| 原则 | 含义 |
|---|---|
| 离线优先 | 任何新功能先问"飞行模式下还能不能用"，不能就必须有降级路径 |
| 契约先行 | 改数据模型或接口必须先改 `packages/shared`，再同步两端 |
| 内容自主撰写 | 条目文案自行改写，禁止整段复制百科，规避抄袭风险 |
| 材料零身份信息 | 所有交付材料不得出现校名、师生姓名、logo |

## 2. 需求拆解矩阵

| 赛题要求 | 我们的实现 | 验收标准 |
|---|---|---|
| **R1** 三维组织 + 关键词检索 | 时间轴（6 时代）+ 城市/类型/时代筛选 + FTS5 BM25 + 端侧 token 匹配 | 飞行模式下输入「洛阳」能出结果，筛选可叠加 |
| **R2** 详情页五层内容 | 六个 Tab：图文 / 考古发现 / 历史事件 / 相关诗词 / 文旅信息 / 关联图谱 | 每 Tab 有真实内容，空数据有优雅占位 |
| **R3** 收藏**遗址与文物条目** + 笔记（文字+时间戳） | 统一收藏表（`targetType` = site / artifact）；笔记带 `createdAt / updatedAt` | 遗址与文物均可收藏、可加笔记，离线可写 |
| **R4** 标签分类管理 | 三预设标签（待实地探访 / 已去过 / 研究资料）+ 自定义 | 按标签筛选收藏 |
| **R5** 学习进度记录与同步 | 定义为「已浏览 ∪ 已收藏 ∪ 已笔记」去重条目数 / 总条目数，按时代分段展示 | 多设备进度一致，数值与定义相符 |
| **R6** 分布式数据管理 + 时间戳冲突策略 | **主路径 HarmonyDistributedKV**；CloudSync 仅作跨网络兜底 | 两端并发改同一条 → 冲突记录可见、按最新时间戳收敛 |
| **R7** 同步状态可视化面板 | 在线状态 / **本次同步进度（n/m 条 + 手机→平板方向）** / 最后同步 / 待推送 / 冲突数 / 来源设备标签 | 面板数字与实际数据一致 |
| **R8** 离线内容浏览 | 全量预置 rawfile，首启导入 RDB | 断网冷启动可浏览全部 80 条 |
| **R9** 智能关联推荐 | 构建期预计算 top-20 邻居 + 行为重排 | 离线可用，推荐理由可解释（如"同属唐三彩"） |
| **I1** 文化主题聚合与个人知识库 | 标签传播自动主题 + 个人知识图谱 + 路径探索 | 收藏 10 条后一键生成主题簇 |
| **I2** 分布式备份恢复 | 全量导出（收藏/笔记/标签/主题/图谱）与恢复 | 导出文件在另一设备完整恢复 |
| **I3** 多端协同编辑与结构化知识文档 | 笔记补充 / 修改 / 合并 / 排序 + LWW 最终一致；**文档视图**按时代与遗址分组聚合、可导出 | 两端分别编辑后内容合并不丢；可导出结构化文档 |
| **加分** 语义检索与 AI 问答 | BM25 + 向量 + RRF + Rerank + 图谱增强 + DeepSeek 流式 | 答案带 `[n]` 引用可跳详情；断网降级抽取式 |

## 4. 数据设计

### 4.1 收录范围

**只收"地点型"文化遗产**，共 **80 条**。按各市遗产资源量**不均等分配**（ADR-014）：

| 城市 | 条数 | 依据 |
|---|---|---|
| 洛阳 | 20 | 世界遗产 + 大量国保，资源最丰 |
| 郑州 | 20 | 含登封"天地之中"系列 + 巩义窑址群 |
| 开封 | 16 | 北宋都城系列，资源集中 |
| 三门峡 | 14 | 仰韶文化核心区 + 虢国墓地 |
| 濮阳 | 10 | 国保数量有限，不强行凑数 |
| **合计** | **80** | |

> 濮阳可用的地点型遗产约 8-10 处，是客观约束；缺口补给洛阳与郑州。

时代轴按赛题六段：**仰韶 → 龙山 → 夏商 → 周 → 汉唐 → 宋**。

**边界处理**：元明清遗产（如登封观星台、金代宝轮寺塔）单独归入"宋以后"延伸分组，UI 上弱化展示，避免与赛题时代轴冲突。对于"始建于某朝、现存建筑为后期重建"的遗产（如开封龙亭、大相国寺），时代按**文化主体**归类，并在文案中明确说明始建与现存建筑的年代差异。

**类型覆盖硬要求**：赛题点名的四类——**都城遗址 / 墓葬群 / 窑址 / 古建筑**——每一类都必须有足量条目（建议每类不少于 6 条），不能出现某一类只有 1 条的塌陷。

**种子候选（待逐条核实）**

| 城市 | 候选遗产（部分） |
|---|---|
| 三门峡 | 仰韶村遗址、庙底沟遗址、虢国墓地（墓葬群）、函谷关、陕州故城、宝轮寺塔（宋以后） |
| 洛阳 | 二里头遗址、偃师商城、汉魏洛阳故城、隋唐洛阳城遗址、邙山陵墓群（墓葬群）、洛阳金村东周墓群（墓葬群）、**新安窑址**（窑址）、龙门石窟、白马寺 |
| 郑州 | 郑州商城遗址、大河村遗址、**巩义窑址（含黄冶三彩窑址）**（窑址）、**密县窑址**（新密，窑址）、**登封窑址**（窑址）、巩义石窟寺、嵩岳寺塔、少林寺、中岳庙 |
| 开封 | 北宋东京城遗址（含州桥遗址）、开宝寺塔（铁塔）、繁塔、大相国寺、龙亭 |

### 4.2 条目模型

```ts
interface HeritageItem {
  id: string                      // 'ly-erlitou'
  name: string                    // '二里头遗址'
  aliases: string[]               // ['偃师二里头', '二里头文化遗址']
  city: '三门峡' | '洛阳' | '郑州' | '开封' | '濮阳'
  era: '仰韶' | '龙山' | '夏商' | '周' | '汉唐' | '宋' | '宋以后'
  eraRange?: [number, number]     // [-1750, -1530]，负数表示公元前
  types: ('都城遗址' | '墓葬群' | '窑址' | '古建筑' | '石窟寺' | '碑刻' | '祭祀址')[]
  level?: '世界遗产' | '全国重点文保' | '省级文保'
  geo: { lat: number; lng: number }
  summary: string                 // 一句话
  intro: string                   // 图文介绍（正文长文）
  archaeology: string             // 考古发现
  events:    { year: string; title: string; desc: string }[]
  poems:     { title: string; author: string; dynasty: string; content: string; note?: string }[]
  travel:    { hours?: string; ticket?: string; best?: string; tips: string[] }
  artifacts: { name: string; desc: string; museum?: string }[]
  figures:   { name: string; role: string; desc: string }[]
  images:    { url: string; caption: string; credit: string; license: string }[]
  keywords:  string[]
  sources:   { title: string; url: string; accessedAt: string }[]
  tokens?:   string[]             // 构建期注入：jieba 分词结果，供端侧检索
}
```

**数据现实与应对**

### 4.5 数据合规红线

1. **必须自行改写撰写**，禁止整段复制百科——赛题明确"严禁抄袭、剽窃"
2. 流水线加**查重自检**：与原始资料做 n-gram 重合度检测，超阈值告警
3. 交付材料中不得出现校名、师生姓名、logo
4. `sources[]` 与 `images[].license` 缺一不可

### 4.6 数据存放位置与离线保障

**三类数据，三处存放**

| 数据类别 | 内容 | 端侧（App） | 云侧（服务器） | 权威源 |
|---|---|---|---|---|
| 公共内容数据 | 条目档案 / 分块 / 词表 / 图谱 / 相似度 / 图片 | **rawfile 全量预置**（权威） | **仅检索索引**：chunk 文本 + 向量 + 图谱 + 筛选元数据；**不含五层完整结构与图片** | 端侧为主 |
| 个人数据 | 收藏 / 笔记 / 标签 / 主题 / 学习进度 | RDB，本地权威，离线可写 | **云存储**：变更日志（增量同步）+ 快照（备份点） | 端侧 |
| 增强结果 | 检索排名 / 问答答案 / 推荐重排 | 不缓存（可选 LRU） | 临时生成，仅统计表落库 | 服务端 |

**关键结论**：公共内容数据必须"**端侧为主、云侧只留检索索引**"。赛题第 4 项明确要求"所有文化资源图文数据均在应用安装时预置本地，用户无需联网即可浏览全部内容"，因此**把档案放服务器上是不行的**——那样必须联网才能浏览，直接违反基础功能要求。

**离线可用性保障（五层）**

| 层 | 机制 |
|---|---|
| 1 打包层 | 全量内容进 rawfile，安装即完整，首启导入 RDB |
| 2 启动层 | 导入完成后，后续每次启动都不再依赖网络 |
| 3 功能层 | 浏览 / 筛选 / 关键词检索 / 收藏 / 笔记 / 标签 / 推荐 / 图谱可视化 全部零网络依赖 |
| 4 降级层 | 服务端不可达时，语义检索与问答自动降级（见 6.2） |
| 5 数据层 | 离线编辑进入「待推送队列」，网络恢复后自动补推 |

**版本一致性**：`meta.json` 记录 `dataVersion` 与 `contentHash`。端侧包与服务端索引必须由**同一次流水线构建**产出，杜绝"手机能搜到、服务器搜不到"。端侧启动时若发现服务端版本更新（选做），仅做提示，不阻塞使用。

**体积预算（图片是唯一的体积风险点）**

| 资源 | 数量级 | 单件 | 小计 |
|---|---|---|---|
| 条目文本（items + chunks） | 80 条 | — | 约 2-4MB |
| 图谱 + 相似度 + 词表 | — | — | 约 1-2MB |
| 图片 | 3-5 张/条 → 240-400 张 | WebP 80-150KB | 约 25-50MB |
| **合计** | | | **约 30-55MB** |

图片统一压缩为 WebP、长边不超过 1080px，另出 200px 缩略图；若超预算，优先降低图片尺寸而非削减条目数量。

### 4.7 服务器职责边界

服务器只干三件事，其余一律不管：

| 职责 | 内容 | 服务的赛题项 |
|---|---|---|
| ① 个人数据云存储 | 同步变更日志（增量）+ 全量快照（备份点与多版本） | R6 多设备同步、I2 备份恢复、加分项"云端存储" |
| ② RAG 检索问答服务 | chunk 向量索引 + BM25 + 图谱增强 + 对接百炼 Rerank 与 DeepSeek | 加分项：语义检索与 AI 问答 |
| ③ 演示辅助（可选） | Web 端只读接口与静态资源（P5 有余量再做） | — |

**服务器不做的**：

- 不掌管档案内容：五层结构与图片的权威副本只在端侧，服务器那份只是"为检索而切出的最小切片"
- 不参与基础功能闭环：浏览、筛选、关键词检索、收藏、笔记、标签、推荐、图谱可视化全部零后端依赖
- 不存图片：RAG 只用文本，服务器磁盘占用小于 100MB

**一个必须说清的物理约束**：RAG 的检索发生在"持有索引的那一侧"。要做**语义检索**，就必须有人把用户 query 编码成向量再去和语料向量算相似度；而端侧不做向量编码（既定决策），所以**语料向量与 chunk 文本必须存在服务端**。这不是我们想多存一份，而是语义检索的物理前提。

如果想彻底让服务器"零语料"，唯一办法是放弃语义检索（只做端侧关键词检索 + 云端 LLM 生成），但那样就丢掉了本作品最主要的差异化点。两种取舍对比：

| 方案 | 服务器持有 | 语义检索 | 图谱增强问答 | 评价 |
|---|---|---|---|---|
| X 零语料 | 只有个人数据 + LLM 代理 | 无 | 无 | 服务器最简单，但加分项基本没了 |
| Y 检索索引 | 个人数据 + chunk 向量索引 + 图谱 | 有 | 有 | **采用**：多存不到 100MB，换回两个核心亮点 |

服务器上那份内容的作用只有一个：让语义检索、图谱推理、AI 问答跑得起来。它整份丢掉时，端侧基础功能不受任何影响。

## 5. 技术架构

```
┌─ 离线流水线（本机执行，不进服务器） ──────────────────────────┐
│ raw.md → jieba 分词 → chunk(300-500字) → embed(百炼,带缓存)    │
│        → graph 三元组 → similar top-20 → export              │
└───────────────────────────┬──────────────────────────────────┘
                            ▼
端侧预置包: items.json / chunks.jsonl(含tokens) / vocab.json
           / graph.json / similar.json / meta.json
                            │
┌─ OpenHarmony 端 (ArkTS) ──┴──────────────────────────────────┐
│ 页面层  P1-P8                                                │
│ 数据层  relationalStore（档案 / 收藏 / 笔记 / 标签 / 进度）      │
│ 服务层  SearchService / GraphService / QaService(WS)         │
│ 同步层  SyncAdapter { HarmonyDistributedKV | CloudSync }      │
│ 身份层  IdentityAdapter { HuaweiOpenId | PairingCode }        │
└───────────────────────────┬──────────────────────────────────┘
                            │ HTTPS / WS
┌─ TS 后端 (Fastify, 2C2G) ─┴──────────────────────────────────┐
│ 检索  BM25(jieba+FTS5) + 向量(百炼) → RRF → Rerank → 过滤      │
│ 问答  图谱增强 → DeepSeek 流式 → 引用 + 图路径                 │
│ 图谱  kg_nodes / kg_edges + BFS / 最短路 / PageRank / 标签传播  │
│ 同步  WS + LWW(updatedAt, deviceId) + 变更日志 + 冲突日志       │
│ 存储  SQLite + 向量索引 + embedding 缓存 + 调用统计            │
└──────────────────────────────────────────────────────────────┘
```

### 5.1 选型理由

| 决策 | 选择 | 理由 |
|---|---|---|
| 生成模型 | DeepSeek 云 API | 2C2G 跑不动本地 LLM；成本可忽略；provider 化便于切换备用 |
| 嵌入 | 阿里云百炼 text-embedding（1024 维） | 国内直连稳定、质量优于本地小模型、免费额度可覆盖建库 |
| 重排 | 百炼 Rerank | 候选 40 → 取 8，显著提升命中质量，成本极低 |
| 向量库 | 不用，暴力余弦 | 几千 chunk 在内存中 3-8ms，引入 Milvus/Qdrant 属过度设计 |
| 图谱存储 | SQLite 两表 | Neo4j 起底需 1GB 内存，2C2G 不可行 |
| 中文分词 | @node-rs/jieba | Rust 实现 + 预编译二进制；让 BM25 的 IDF 具备实际意义 |
| 后端框架 | Fastify | 比 NestJS 省一半内存，性能足够 |
| 同步身份 | 华为 openid 主 + 配对码兜底 | 前者贴合鸿蒙生态，后者保证资质受限时功能不瘫 |
| 同步通道 | **distributedKVStore 为主，CloudSync 为兜底** | 赛题把"基于鸿蒙分布式数据服务"列为主要功能，把"云端存储"列为加分项，主次不可颠倒 |

### 5.2 资源预算（2C2G 服务器）

| 组件 | 常驻内存 |
|---|---|
| Node + Fastify | 约 120MB |
| 向量 + BM25 索引 | 约 20MB |
| SQLite 页缓存 | 约 32MB |
| Caddy | 约 30MB |

采用云嵌入方案后，无需在服务器常驻本地 ONNX 模型（可省约 250MB），这是该方案的隐性收益。

## 6. 检索与问答设计

### 6.1 双通道检索链

```
用户查询「洛阳的唐代窑址」
 ├─ 查询理解：实体词典识别 → city=洛阳, era=汉唐, type=窑址（结构化过滤）
 ├─ 通道 A：jieba 分词 → FTS5 BM25 top20         （专名精确，纯本地）
 ├─ 通道 B：百炼编码 query → 余弦 top20           （语义召回，LRU 缓存）
 ├─ RRF 融合两路排名
 ├─ 百炼 Rerank 取 top8
 ├─ 图谱增强：命中实体取 1-2 跳子图，邻居名拼入查询扩展
 └─ DeepSeek 流式生成（只依据片段作答 + 每条结论标 [n]）
```

**jieba 的确切位置**：仅用于服务端 FTS5 的预分词与 BM25 词频统计。**分词结果不进嵌入、不进大模型上下文**；chunk 原文原封不动地交给嵌入模型与 LLM。

**端侧对应实现**：构建期把 `tokens` 与语料 `vocab` 一并打包，端侧用词典最大匹配做查询切分，与服务器共用同一套词表，保证两端检索结果基本一致。

**端侧检索需双保险**：分词匹配之外，同时保留**原文子串匹配**（对未登录词、错字、单字输入兜底），避免用户输入词典里没有的词时返回零结果。命中结果按"分词命中 > 子串命中"排序。

### 6.2 四级降级链（路演保命设计）

| 故障 | 降级动作 |
|---|---|
| Rerank 接口抖动 | 跳过重排，直接使用 RRF 结果 |
| 向量接口抖动 | 仅 BM25 关键词检索 |
| DeepSeek 不可用 | 抽取式回答：Top-3 片段摘要 + 引用卡片 |
| 完全断网 | 端侧 token 匹配检索 + 预计算关联推荐 + 本地全文浏览 |

### 7.2 算法

| 算法 | 用途 |
|---|---|
| 1-2 跳邻域展开 | 图谱问答与可视化取数 |
| BFS 最短路（带权） | 路径探索，如"从仰韶到宋的文化脉络" |
| PageRank | 节点权重（决定可视化节点大小与推荐排序） |
| **标签传播社区发现** | **自动文化主题聚合（创新点 I1 核心）** |
| 邻域 Jaccard 相似度 | 关联推荐补充 |

### 7.3 可视化

Canvas 2D 力导向布局（网格桶近似保证 500 节点内流畅）：

- 节点按类型着色、大小按 PageRank
- 边按关系类型区分实线 / 虚线
- **时间轴联动**：拖动时代轴，对应时代的节点高亮放大，其余淡出
- **聚类动画**：新主题生成时，相关节点向簇心收拢的补间动画
- 交互：单击展开邻居、双击跳详情、长按加入主题

## 8. 分布式与同步设计

### 8.1 双通道架构

```ts
interface SyncAdapter {
  push(changes: Change[]): Promise<void>
  pull(since: number): Promise<Change[]>
  subscribe(cb: (c: Change[]) => void): () => void
  status(): { online: boolean; lastSync: number; pending: number; conflicts: number }
}
```

| 通道 | 实现 | 定位 | 使用场景 |
|---|---|---|---|
| A | HarmonyDistributedKV（**鸿蒙分布式数据服务**） | **主路径**：实现赛题主要功能第 3 项 | 同华为账号 + 超级终端信任环的真机对真机 |
| B | CloudSync（WebSocket + 服务端变更日志） | **兜底与加分**：实现"云端存储"加分项，并保证演示与跨网络场景可用 | 跨网络、路演第二设备、真机数量不足时 |

**主次纪律**：无论演示与否，通道 A 的代码必须完整、可自环运行，并在答辩时优先说明。通道 B 的定位是"当分布式软总线不可用时的补充"，不能替代 A 成为主方案——赛题把"基于鸿蒙分布式数据服务"写在主要功能里，把"云端存储"写在加分项里，这个主次关系答错会直接失分。

### 8.2 身份绑定

```ts
interface IdentityAdapter {
  currentUser(): Promise<{ id: string; type: 'openid' | 'paired' } | null>
  bind(): Promise<void>   // openid 走 Account Kit；paired 走配对码
}
```

| 路径 | 实现 | 风险与对策 |
|---|---|---|
| 主：华为账号 openid | Account Kit 获取同一账号下的匿名标识 | 需 AppGallery Connect 建应用 + 签名证书 + 申请权限，个人开发者可用性待验证；验证不通立即切兜底 |
| 兜底：配对码 | 设备 A 生成 6 位码 / 二维码，设备 B 输入即绑定同一身份 | 零依赖，路演现场 30 秒可演示 |

### 8.3 冲突策略

严格按赛题要求：**最新时间戳为准**（LWW，`updatedAt` 毫秒 + `deviceId` 兜底打破平局）。

冲突写入 `conflict_log`，同步中心展示：双方版本、时间戳、最终采用哪一方、可展开查看差异。

**同步进度可视化**（对应赛题原文"清晰展示'手机→平板'的同步进度"）：同步过程中展示方向标识（手机 → 平板）、已完成条数/总条数（n/m）与进度条；`SyncAdapter.status()` 增加 `progress: { done: number; total: number; direction: string }` 字段。

### 8.4 备份恢复与协同编辑

- **备份**：全量导出（收藏 / 笔记 / 标签 / 主题 / 图谱快照）为 JSON；**本地备份 + 云端快照双份**，云端快照由服务器保存为带时间戳的版本点，支持回滚到任意备份点
- **恢复**：导入后按 LWW 合并，不覆盖更新的本地版本；换机时凭身份绑定直接拉取云端最新快照
- **协同编辑**：笔记支持补充、修改、合并、排序；端侧维护「本地待推送队列」，保证离线编辑最终一致
- **结构化知识文档**（对应赛题原文"形成结构化知识文档"）：提供**文档视图**，把同一主题下的多条笔记按"时代 → 遗址"两级分组聚合为一份结构化文档，支持自定义排序与一键导出（Markdown / 纯文本），构成可交付的学习成果

### 10.2 流水线脚本

### 15.2 术语表

| 术语 | 含义 |
|---|---|
| 条目 | 一处地点型文化遗产的完整档案记录 |
| chunk | 条目正文按语义切出的检索片段（300-500 字） |
| token | jieba 切出的词，用于 BM25 索引与打分 |
| RRF | Reciprocal Rank Fusion，倒数排名融合，用于合并两路检索结果 |
| 双通道同步 | 主路径 HarmonyDistributedKV 与兜底通道 CloudSync |
| 检索索引 | 服务器持有的最小数据集（chunk 文本 + 向量 + 图谱 + 元数据），仅服务于语义检索与问答 |
| 文档视图 | 把同一主题下多条笔记按时代与遗址聚合为可导出的结构化文档 |
| LWW | Last Write Wins，按最新时间戳决定冲突胜出版本 |
| 标签传播 | 图社区发现算法，用于自动生成文化主题簇 |
