## ADR-001 采用 HarmonyOS SDK

- **日期**：2026-09-21 ｜ **状态**：已采纳
- **背景**：赛题写"基于 OpenHarmony 开发"，要求 API 版本 12 及以上；团队只有华为真机，无开发板
- **决策**：使用 DevEco Studio 26.0.0 内置的 HarmonyOS SDK 26.0.0（API 26）。该 SDK 由 `openharmony/`（基础 API）与 `hms/`（华为专有服务）两部分组成，编译产出 HarmonyOS 应用
- **备选**：纯 OpenHarmony SDK + 开发板
- **理由**：赛题原文写明"纯北向应用类赛题使用鸿蒙手机、平板或模拟器即可完成开发，无需额外采购硬件"，而 OpenHarmony 几乎没有消费级整机；HarmonyOS 的应用开发在技术栈上与 OpenHarmony 同源（同一套 ArkTS / ArkUI / API）
- **影响**：可使用 Account Kit 等华为专有能力；`compatibleSdkVersion` 定为 17（工具链下限），覆盖 HarmonyOS 5.1 及以上设备

## ADR-002 生成模型采用 DeepSeek 云 API

- **日期**：2026-09-21 ｜ **状态**：已采纳
- **背景**：2C2G 服务器无法常驻有价值的本地大模型；问答需要流式生成
- **决策**：问答生成走 DeepSeek `deepseek-chat` 云 API，流式返回；接口按 provider 抽象，可一键切换厂商
- **备选**：本地 llama.cpp + Qwen2.5-0.5B/1.5B 量化模型
- **理由**：2C2G 上本地小模型速度仅 5-10 tok/s 且质量差，演示风险高；云 API 成本可忽略（全项目预计 1 元以内），质量满足需求
- **影响**：路演依赖外网。已通过四级降级链规避——DeepSeek 不可用时自动降级为抽取式回答（Top-3 片段摘要 + 引用），功能不中断

## ADR-003 嵌入与重排采用阿里云百炼

- **日期**：2026-09-21 ｜ **状态**：已采纳（型号待 P0 实测确定）
- **背景**：语义检索需要把 chunk 与查询编码为向量；服务器 2C2G
- **决策**：嵌入用百炼通义 text-embedding（取最新可用型号，维度锁 1024），重排用百炼 Rerank（候选 40 → 取 8）
- **备选**：本地 bge-small-zh-v1.5（ONNX，约 95MB，常驻约 250MB）
- **理由**：省去服务器约 250MB 常驻内存；国内直连稳定；质量优于本地小模型；建库总花费不足 1 元
- **影响**：端侧无法对新查询做向量编码，语义检索只能在联网时使用（见 ADR-004）。索引与查询必须使用同一模型同一维度，否则向量空间不一致

## ADR-004 端侧不做语义检索

- **日期**：2026-09-21 ｜ **状态**：已采纳
- **背景**：采用云嵌入后，端侧即使预置语料向量也无法为用户的任意查询编码向量
- **决策**：端侧只做关键词检索（分词匹配 + 原文子串兜底）+ 别名同义词扩展 + 预计算关联推荐；语义检索作为联网增强
- **备选**：端侧嵌入 ONNX 运行时 + 小模型（约 100MB 包体增量）
- **理由**：赛题硬要求是"离线浏览"与"关键词检索"，"语义检索"属加分项。为此引入鸿蒙 NAPI 集成 ONNX 风险高（约一周工作量），收益仅是飞行模式下多一条检索通道
- **影响**：端侧预置包不包含向量文件，包体更小；端侧与服务端共用同一套词表以保证检索结果一致

## ADR-005 不引入向量数据库与图数据库

- **日期**：2026-09-21 ｜ **状态**：已采纳
- **背景**：需要向量检索与图关系推理；服务器 2C2G
- **决策**：向量用 Float32Array 暴力余弦；图用 SQLite 两张表（`kg_nodes` / `kg_edges`）；两者都跑在 Node 进程内
- **备选**：Milvus / Qdrant（向量库）、Neo4j（图库）
- **理由**：语料为 600-1500 个 chunk，512-1024 维向量在内存中做暴力 kNN 仅需 3-8ms，引入向量库属过度设计；Neo4j 仅 JVM 起底就需约 1GB 内存，2C2G 上不可行
- **影响**：服务器常驻内存控制在约 200MB；chunk 规模超过 1 万时可平滑替换为 `sqlite-vec` 扩展

## ADR-006 中文分词方案

- **日期**：2026-09-21 ｜ **状态**：已采纳
- **背景**：SQLite FTS5 默认分词器对中文无效（整段会被当作一个 token），BM25 的 IDF 统计也失去意义
- **决策**：服务端用 `@node-rs/jieba` 预分词（含自定义词典，灌入 5 城 / 6 时代 / 类型词 / 遗址别名）；端侧不装分词器，改由构建期预置 `tokens` 字段与语料词表（约 100KB），端侧用词典最大匹配切分查询
- **备选**：`nodejieba`（需编译、已停维护）、纯 JS `segment`（慢且准确率低）、FTS5 `trigram` 分词器（索引膨胀且无词权重）
- **理由**：jieba 的词边界让「二里头」「仰韶」这类专名成为独立 term，IDF 才有意义；Rust 实现带预编译二进制，零编译成本
- **影响**：分词结果只用于 FTS5 索引列与 BM25 打分，**不进嵌入、不进大模型上下文**——chunk 原文原封不动地交给嵌入模型与 LLM

## ADR-007 同步双通道，鸿蒙分布式为主

- **日期**：2026-09-21 ｜ **状态**：已采纳
- **背景**：赛题把"基于鸿蒙分布式数据服务"列为主要功能第 3 项，把"云端存储"列为加分项；团队只有 1 台真机
- **决策**：`SyncAdapter` 抽象双实现——通道 A `HarmonyDistributedKV`（分布式数据服务）为主路径；通道 B `CloudSync`（WebSocket + 服务端变更日志）为兜底与跨网络补充
- **备选**：只做 CloudSync（放弃分布式数据服务）
- **理由**：主次关系由赛题原文决定，答错会直接失分；而单设备条件下真机演示分布式同步困难，需要兜底通道保证演示可用
- **影响**：通道 A 的代码必须完整、可自环运行，答辩时优先说明；通道 B 定位为"分布式软总线不可用时的补充"，不得替代 A

## ADR-008 身份绑定：openid 主 + 配对码兜底

- **日期**：2026-09-21 ｜ **状态**：已采纳
- **背景**：鸿蒙分布式同步靠华为账号建立信任环，但自建 CloudSync 通道需要自己的身份标识
- **决策**：`IdentityAdapter` 抽象——主方案用 Account Kit 获取同一华为账号下的 openid；兜底方案用 6 位配对码 / 二维码绑定同一身份
- **备选**：自建账号密码体系（多出注册登录页）
- **理由**：openid 最贴合鸿蒙生态且无需自建账号；但其依赖 AppGallery Connect 建应用、签名证书与权限申请，个人开发者可用性未验证，必须有零依赖兜底
- **影响**：即使 openid 路径不通，同步功能仍完整可用；配对码方案是路演现场最快的绑定方式（约 30 秒）

## ADR-009 服务器只承担两件事

- **日期**：2026-09-22 ｜ **状态**：已采纳
- **背景**：早期方案中服务器承担语义检索、图谱推理、问答、同步中转四项职责，与端侧功能边界模糊
- **决策**：服务器职责收敛为①个人数据云存储（同步变更日志 + 备份快照）②RAG 检索问答服务。不掌管档案内容、不存图片、不参与基础功能闭环
- **备选**：让服务器承载全部内容并提供 `/api/items` 供端侧调用
- **理由**：赛题要求"所有文化资源图文数据均在应用安装时预置本地"，端侧才是内容权威；服务器职责越少，答辩叙事越清晰，也越容易证明"服务器整份挂掉，App 依然完整可用"
- **影响**：端侧 App 一行都不调用 `/api/items`（该接口仅供 Web 演示端与调试）；服务器磁盘占用小于 100MB

## ADR-010 内容数据端侧权威、云侧只留检索索引

- **日期**：2026-09-22 ｜ **状态**：已采纳
- **背景**：需要明确公共内容数据放在哪一侧
- **决策**：条目的五层完整结构与图片**只在端侧**（rawfile 预置）；服务器只保留"为检索而切出的最小切片"——chunk 文本 + 向量 + 图谱 + 筛选元数据
- **备选**：服务器保存完整档案副本；或彻底不上服务器（放弃语义检索）
- **理由**：RAG 的检索发生在持有索引的一侧。端侧不做向量编码（ADR-004），所以语料向量必须在服务端——这是语义检索的物理前提，不是冗余存储
- **影响**：`export` 脚本一次构建产出两份产物（端侧全量包 + 服务端检索索引），版本号一致，杜绝"手机能搜到、服务器搜不到"

## ADR-011 工程命名与最低兼容版本

- **日期**：2026-09-29 ｜ **状态**：已采纳
- **背景**：包名后期改动成本高（连带签名配置与 AGC 注册），需一次定死
- **决策**：鸿蒙工程名 `YellowRiverArchive`，包名 `com.yellowriver.archive`，`compatibleSdkVersion` = 17
- **备选**：用队名或学校拼音命名；`compatibleSdkVersion` 设为 26（与 SDK 一致）
- **理由**：工程命名保持中性，不含校名与队名，符合提交材料的匿名要求；API 17 是工具链允许的下限，覆盖范围最广，避免现场演示设备版本过低装不上
- **影响**：代码只允许使用 API 17 可用的基础能力，不得使用新特性

## ADR-013 图片策略：主图必配 + 补充可选

- **日期**：2026-09-22 ｜ **状态**：已采纳
- **背景**：五层内容都要配图，全套 3-5 张/条将产生 240-400 张图，找图与版权核查工作量巨大
- **决策**：每条必须配 1 张主图（共 80 张），关键遗址再补 2-3 张（约 150 张）；统一 WebP、长边 ≤1080px、另出 200px 缩略图；主图由条目撰写人负责，补充图由 C 统一补
- **备选**：每条 3-5 张全套；或图片最少、靠自绘示意图
- **理由**：图片是安装包体积的唯一风险点（约 25-50MB），也是版权风险集中处；主图必配保证观感底线，补充图按资源情况弹性处理
- **影响**：预计总图量约 230 张，安装包控制在 30-55MB

## ADR-014 数据规模与城市分配

- **日期**：2026-09-22 ｜ **状态**：已采纳
- **背景**：赛题沿黄城市为三门峡 / 洛阳 / 郑州 / 开封 / 濮阳，但各市遗产资源量差别很大
- **决策**：共 80 条，不均等分配——洛阳 20 / 郑州 20 / 开封 16 / 三门峡 14 / 濮阳 10
- **备选**：五城均分 16 条
- **理由**：濮阳的国保单位数量有限，可用的地点型遗产约 8-10 处，强行凑到 16 条只能拉低质量；把差额补给资源更丰富的洛阳与郑州
- **影响**：`sites.yaml` 需按此配额校验各城条目数，缺口提前预警

## ADR-015 内容生产流程：AI 起草 + 人工改写

- **日期**：2026-09-22 ｜ **状态**：已采纳
- **背景**：80 条 × 五层内容约 15-20 万字，纯人工撰写周期过长；赛题严禁抄袭剽窃
- **决策**：六步流水线——人工来源摘录 → AI 起草（输出草稿，禁止直接入库）→ 人工改写 → 交叉校对（校对人与撰写人不得相同）→ 自动质检（含 n-gram 查重）→ 入库
- **备选**：纯人工撰写（慢）；直接由 AI 生成后入库（抄袭与事实风险高）
- **理由**：来源摘录让 AI 有据可依、改写有对照、`sources` 字段自动有据可填；人工改写负责去 AI 腔与事实核对；查重脚本以"与来源连续重合 ≤15 字"为红线
- **影响**：中间产物（`drafts/` 与 `sites/`）都是人可编辑的 YAML，便于 diff 与评审

## ADR-016 开发顺序：先端侧垂直切片

- **日期**：2026-09-30 ｜ **状态**：已采纳
- **背景**：端侧是评分主体，后端是加分项；数据工程是长尾工作
- **决策**：先做 P0 地基（仓库 + 契约 + 工程骨架 + 四个技术验证），再用 3-5 条手写数据跑通端侧"浏览 → 检索 → 详情"垂直切片，然后数据工程与后端并行推进
- **备选**：数据与后端先行，端侧后做
- **理由**：先用最小数据量验证环境、RDB、UI 框架与数据契约，避免契约错误导致两端返工；数据工程可以长尾并行，不应阻塞代码
- **影响**：P1 阶段只需 5 条数据，不要等 80 条写完才动手

## ADR-017 使用真机开发，不下模拟器镜像

- **日期**：2026-09-30 ｜ **状态**：已采纳
- **背景**：模拟器镜像需 30 分钟以上下载且占用磁盘；团队有 1 台华为真机

## ADR-018 协作方式

- **日期**：2026-09-22 ｜ **状态**：已采纳
- **背景**：三人协作，需要轻量但明确的协作规则
- **决策**：GitHub 私有仓；简化分支模型（`main` / `feat/*` / `fix/*` / `data/*`）；本地 `.githooks` 钩子（pre-commit 快检查、pre-push 重量检查），不启用 CI；任务与进度用仓库内 `docs/board.md` 看板
- **备选**：标准分支模型（含 dev 分支）；GitHub Actions；Issues + Projects
- **理由**：三人规模下多一层 dev 分支只增加合并开销；国内访问 GitHub Actions 不稳定；看板放在仓库里评审时可直接打开看
- **影响**：合并纪律靠评审而非工具强制，改契约的 PR 必须两端各 1 人看过

## ADR-019 共享契约必须写成 ArkTS 子集

- **日期**：2026-10-05 ｜ **状态**：已采纳
- **背景**：D0 阶段实测发现，把普通 TypeScript 声明文件原样生成为端侧 `.ets` 时，`devecocli check arkts` 报出 **42 个错误**，全部集中在 6 类语法上
- **决策**：`packages/shared` 中会被生成到端侧的四个文件（`constants` / `models` / `preset` / `api`）一律写成 **ArkTS 子集**；`tools/gen` 只做逐字复制 + 加头，不做语法转换
- **备选**：让生成器做 TS → ArkTS 的语法转换
- **理由**：转换器需要维护一张语法映射表，随两端语言演进而持续失效；写成子集则两端共用同一份源码，零转换、零漂移，且 `devecocli check arkts` 可直接当作契约的守门人
- **影响**：以下语法在整个共享契约中**禁用**：

| 禁用语法 | 报错规则 | 替代写法 |
|---|---|---|
| `as const` | `arkts-no-as-const` | 显式标注类型的数组：`const X: T[] = [...]` |
| `(typeof X)[number]` | `arkts-no-aliases-by-index` | 手写字符串字面量联合类型 |
| `typeof` 类型查询 | `arkts-no-type-query` | 同上 |
| 内联对象类型 `{ a: number }` | `arkts-no-obj-literals-as-types` | 声明具名 `interface` |
| 未标注类型的对象字面量 | `arkts-no-untyped-obj-literals` | 先声明 interface 再标注 |
| 数组展开 `[...a, b]` | `arkts-no-spread` | 逐项写全 |

- **额外收益**：手写的 ArkTS 代码（Index / 各页面 / 主题常量）在同一轮检查中**零错误**，说明子集约束一旦建立，端侧代码质量可被工具持续验证

## ADR-020 D0-V 四项技术验证结论

- **日期**：2026-10-05 ｜ **状态**：已采纳
- **背景**：D0 地基完成后，四个关键技术假设需要在真机上实测才能确定后续设计；服务器与端侧的性能预算都建立在这些假设上
- **测试设备**：华为畅享 90 Pro Max（API 26）
- **决策**：依据下列实测结果调整设计（见「影响」）

| 验证 | 测试内容 | 结果 |
|---|---|---|
| **D0V-1** 分布式键值库 | KVManager 创建、协作型存储打开、增/读/前缀遍历/删 | **通过**（首次 574ms，含初始化；后续 79ms；写 3 条 29ms） |
| **D0V-2** 关系型存储 | RDB 建表 + 批量写入 1000 条（每条约 250 字）+ 全表扫描 + 条件查询 | **通过**（批量写入 **50ms**，全表扫描 0ms，条件查询 2-3ms） |
| **D0V-4** 图片资源加载 | rawfile 串行读取 50 张 WebP（1080×720，单张 136KB，共 6.5MB） | **通过**（总耗 **11ms**） |
| **D0V-3** 力导向布局 | Canvas 绘制 200 节点 / 300 连边，含斥力+弹簧+向心+阻尼，连跑 60 帧 | **通过**（**6.57ms/帧**，折算 152fps） |

**影响**：

1. **首启导入不需要进度条或分片导入**。全量预计 80 条档案 + 约 1500 个 chunk，按实测速度约 100ms 完成
2. **图片尺寸策略维持不变**（WebP、长边 1080px、单张 80-150KB）。230 张图片读取约 100ms，不是瓶颈；体积预算的约束仍然是安装包大小而非性能
3. **图谱页可直接用朴素力导向，但仅在 200-300 节点范围内**。斥力是 O(n²)：200 节点 6.57ms/帧，推算 500 节点约需 35ms/帧（约 28fps），**届时必须启用网格桶近似**（与 设计文档 §7.3 一致）
4. **distributedKVStore 可用**，本地读写、前缀遍历、删除全部正常，耗时在毫秒级，完全能承载收藏/笔记/标签的写入量

**遗留**：真正的**跨设备同步**尚未验证——directional 同步需要第二台可信设备。当前只有一台真机，需借机或临时下载 tablet 模拟器镜像补验（见看板 B1）。通道 A 的代码可先按 API 文档实现，待第二台设备到位后一次验证。

> 验证代码：`harmony/YellowRiverArchive/entry/src/main/ets/service/DevProbe.ets` 与 `utils/ForceProbe.ets`；验证截图存本地 `.shots/`（已 gitignore）。验证完成后这两个文件可整体删除。

## ADR-021 ArkTS 的 @Builder 只接静态标识，状态一律用 this 读

- **日期**：2026-10-05 ｜ **状态**：已采纳
- **背景**：D1 检索页的第一版把筛选状态当参数传进 `@Builder filterRow(title, values, selected, onToggle)`。实测表现：点击筛选 chip 后界面**不刷新**（选中态不变），且检索引擎收到的条件与界面显示不一致
- **决策**：`@Builder` 只接收**静态标识**（如 `'city'` / `'era'` / `'type'`），凡参与渲染的可变状态一律在 Builder 内部通过 `this.xxx` 直接读取
- **备选**：用 `$$` 双向绑定；或完全放弃 Builder、把 UI 内联到 `build()`
- **理由**：ArkTS 中 `@Builder` 的**值参数按值传递，不具备响应性**——参数变化不会触发 Builder 内 UI 刷新，而状态赋值是生效的，于是造成"数据变了但界面不变"的隐蔽不一致。通过 `this` 读取状态时，Builder 会随组件重渲染而重新执行
- **影响**：写进 [开发规范](./开发规范.md) §4.2，列为端侧编码硬规则；本次修复后筛选 chip 选中态与检索引擎条件恢复一致（已在模拟器上验证）
- **另一条并发约定**：异步检索必须在**调用点锁定**查询串与筛选条件（`const query = this.keyword`），再进入 await，避免 await 期间状态变化导致"结果与展示不符"

## ADR-022 数据核实改为「领域知识初稿 + 人工核对」双轨

- **日期**：2026-10-05 ｜ **状态**：已采纳
- **背景**：原计划由 Agent 联网核实 80 条清单的城市归属、年代、类型、文保级别与坐标。实测网络环境后否决了该路径
- **实测结果**：

| 源 | 可达性 | 可否抓取 |
|---|---|---|
| Wikidata SPARQL | 不可达 | — |
| 中文维基百科 | 不可达 | — |
| 百度百科 | 可达 | **需验证码**，不可抓取 |
| 中国大百科全书 | 可达 | JS 单页应用，内容不由 HTML 返回 |
| 国家文物局（不可移动文物信息） | 可达 | JS 动态渲染，名录链接均为 `javascript:;`，无可直接调用的接口 |

- **决策**：改为双轨制
  1. **Agent 侧**：基于领域知识产出带**置信度标注**的清单草稿（`sites.yaml`），仅对高置信项标 `已核`
  2. **人工侧**：队友用浏览器按核对清单逐项确认（产出 `docs/data-verify-checklist.md`）
- **备选**：自行搭建维基镜像；用付费商业数据接口；只收录能自动核实的少量条目
- **理由**：前两者成本超出学生团队范围；后者会让 80 条规模目标落空。双轨制把机器能做好的（结构、一致性、分布校验）交给机器，把需要人判断的（事实核对）交给人，且**不假装置信**
- **影响**：`sites.yaml` 增加 `confidence`（high/medium/low）与 `status`（已核/待核/存疑）两个字段；置信度为 low 的条目**不得进入 P0 批次**，且在核对完成前不写正文
