## ADR-001 采用 HarmonyOS SDK

- **日期**：2026-09-21 ｜ **状态**：已采纳
- **背景**：赛题写"基于 OpenHarmony 开发"，要求 API 版本 12 及以上；团队只有华为真机，无开发板
- **决策**：使用 DevEco Studio 26.0.0 内置的 HarmonyOS SDK 26.0.0（API 26）。该 SDK 由 `openharmony/`（基础 API）与 `hms/`（华为专有服务）两部分组成，编译产出 HarmonyOS 应用
- **备选**：纯 OpenHarmony SDK + 开发板
- **理由**：赛题原文写明"纯北向应用类赛题使用鸿蒙手机、平板或模拟器即可完成开发，无需额外采购硬件"，而 OpenHarmony 几乎没有消费级整机；HarmonyOS 的应用开发在技术栈上与 OpenHarmony 同源（同一套 ArkTS / ArkUI / API）
- **影响**：可使用 Account Kit 等华为专有能力；`compatibleSdkVersion` 定为 17（工具链下限），覆盖 HarmonyOS 5.1 及以上设备

## ADR-002 生成模型采用 DeepSeek 云 API

- **日期**：2026-09-21 ｜ **状态**：已采纳
- **背景**：2C2G 服务器无法常驻有价值的本地大模型；问答需要流式生成
- **决策**：问答生成走 DeepSeek `deepseek-chat` 云 API，流式返回；接口按 provider 抽象，可一键切换厂商
- **备选**：本地 llama.cpp + Qwen2.5-0.5B/1.5B 量化模型
- **理由**：2C2G 上本地小模型速度仅 5-10 tok/s 且质量差，演示风险高；云 API 成本可忽略（全项目预计 1 元以内），质量满足需求
- **影响**：路演依赖外网。已通过四级降级链规避——DeepSeek 不可用时自动降级为抽取式回答（Top-3 片段摘要 + 引用），功能不中断

## ADR-003 嵌入与重排采用阿里云百炼

- **日期**：2026-09-21 ｜ **状态**：已采纳（型号待 P0 实测确定）
- **背景**：语义检索需要把 chunk 与查询编码为向量；服务器 2C2G
- **决策**：嵌入用百炼通义 text-embedding（取最新可用型号，维度锁 1024），重排用百炼 Rerank（候选 40 → 取 8）
- **备选**：本地 bge-small-zh-v1.5（ONNX，约 95MB，常驻约 250MB）
- **理由**：省去服务器约 250MB 常驻内存；国内直连稳定；质量优于本地小模型；建库总花费不足 1 元
- **影响**：端侧无法对新查询做向量编码，语义检索只能在联网时使用（见 ADR-004）。索引与查询必须使用同一模型同一维度，否则向量空间不一致

## ADR-004 端侧不做语义检索

- **日期**：2026-09-21 ｜ **状态**：已采纳
- **背景**：采用云嵌入后，端侧即使预置语料向量也无法为用户的任意查询编码向量
- **决策**：端侧只做关键词检索（分词匹配 + 原文子串兜底）+ 别名同义词扩展 + 预计算关联推荐；语义检索作为联网增强
- **备选**：端侧嵌入 ONNX 运行时 + 小模型（约 100MB 包体增量）
- **理由**：赛题硬要求是"离线浏览"与"关键词检索"，"语义检索"属加分项。为此引入鸿蒙 NAPI 集成 ONNX 风险高（约一周工作量），收益仅是飞行模式下多一条检索通道
- **影响**：端侧预置包不包含向量文件，包体更小；端侧与服务端共用同一套词表以保证检索结果一致

## ADR-005 不引入向量数据库与图数据库

- **日期**：2026-09-21 ｜ **状态**：已采纳
- **背景**：需要向量检索与图关系推理；服务器 2C2G
- **决策**：向量用 Float32Array 暴力余弦；图用 SQLite 两张表（`kg_nodes` / `kg_edges`）；两者都跑在 Node 进程内
- **备选**：Milvus / Qdrant（向量库）、Neo4j（图库）
- **理由**：语料为 600-1500 个 chunk，512-1024 维向量在内存中做暴力 kNN 仅需 3-8ms，引入向量库属过度设计；Neo4j 仅 JVM 起底就需约 1GB 内存，2C2G 上不可行
- **影响**：服务器常驻内存控制在约 200MB；chunk 规模超过 1 万时可平滑替换为 `sqlite-vec` 扩展

## ADR-006 中文分词方案

- **日期**：2026-09-21 ｜ **状态**：已采纳
- **背景**：SQLite FTS5 默认分词器对中文无效（整段会被当作一个 token），BM25 的 IDF 统计也失去意义
- **决策**：服务端用 `@node-rs/jieba` 预分词（含自定义词典，灌入 5 城 / 6 时代 / 类型词 / 遗址别名）；端侧不装分词器，改由构建期预置 `tokens` 字段与语料词表（约 100KB），端侧用词典最大匹配切分查询
- **备选**：`nodejieba`（需编译、已停维护）、纯 JS `segment`（慢且准确率低）、FTS5 `trigram` 分词器（索引膨胀且无词权重）
- **理由**：jieba 的词边界让「二里头」「仰韶」这类专名成为独立 term，IDF 才有意义；Rust 实现带预编译二进制，零编译成本
- **影响**：分词结果只用于 FTS5 索引列与 BM25 打分，**不进嵌入、不进大模型上下文**——chunk 原文原封不动地交给嵌入模型与 LLM

## ADR-007 同步双通道，鸿蒙分布式为主

- **日期**：2026-09-21 ｜ **状态**：已采纳
- **背景**：赛题把"基于鸿蒙分布式数据服务"列为主要功能第 3 项，把"云端存储"列为加分项；团队只有 1 台真机
- **决策**：`SyncAdapter` 抽象双实现——通道 A `HarmonyDistributedKV`（分布式数据服务）为主路径；通道 B `CloudSync`（WebSocket + 服务端变更日志）为兜底与跨网络补充
- **备选**：只做 CloudSync（放弃分布式数据服务）
- **理由**：主次关系由赛题原文决定，答错会直接失分；而单设备条件下真机演示分布式同步困难，需要兜底通道保证演示可用
- **影响**：通道 A 的代码必须完整、可自环运行，答辩时优先说明；通道 B 定位为"分布式软总线不可用时的补充"，不得替代 A

## ADR-008 身份绑定：openid 主 + 配对码兜底

- **日期**：2026-09-21 ｜ **状态**：已采纳
- **背景**：鸿蒙分布式同步靠华为账号建立信任环，但自建 CloudSync 通道需要自己的身份标识
- **决策**：`IdentityAdapter` 抽象——主方案用 Account Kit 获取同一华为账号下的 openid；兜底方案用 6 位配对码 / 二维码绑定同一身份
- **备选**：自建账号密码体系（多出注册登录页）
- **理由**：openid 最贴合鸿蒙生态且无需自建账号；但其依赖 AppGallery Connect 建应用、签名证书与权限申请，个人开发者可用性未验证，必须有零依赖兜底
- **影响**：即使 openid 路径不通，同步功能仍完整可用；配对码方案是路演现场最快的绑定方式（约 30 秒）

## ADR-009 服务器只承担两件事

- **日期**：2026-09-22 ｜ **状态**：已采纳
- **背景**：早期方案中服务器承担语义检索、图谱推理、问答、同步中转四项职责，与端侧功能边界模糊
- **决策**：服务器职责收敛为①个人数据云存储（同步变更日志 + 备份快照）②RAG 检索问答服务。不掌管档案内容、不存图片、不参与基础功能闭环
- **备选**：让服务器承载全部内容并提供 `/api/items` 供端侧调用
- **理由**：赛题要求"所有文化资源图文数据均在应用安装时预置本地"，端侧才是内容权威；服务器职责越少，答辩叙事越清晰，也越容易证明"服务器整份挂掉，App 依然完整可用"
- **影响**：端侧 App 一行都不调用 `/api/items`（该接口仅供 Web 演示端与调试）；服务器磁盘占用小于 100MB

## ADR-010 内容数据端侧权威、云侧只留检索索引

- **日期**：2026-09-22 ｜ **状态**：已采纳
- **背景**：需要明确公共内容数据放在哪一侧
- **决策**：条目的五层完整结构与图片**只在端侧**（rawfile 预置）；服务器只保留"为检索而切出的最小切片"——chunk 文本 + 向量 + 图谱 + 筛选元数据
- **备选**：服务器保存完整档案副本；或彻底不上服务器（放弃语义检索）
- **理由**：RAG 的检索发生在持有索引的一侧。端侧不做向量编码（ADR-004），所以语料向量必须在服务端——这是语义检索的物理前提，不是冗余存储
- **影响**：`export` 脚本一次构建产出两份产物（端侧全量包 + 服务端检索索引），版本号一致，杜绝"手机能搜到、服务器搜不到"

> **后注（ADR-024 修正）**：本条的执行口径需要收窄。「内容只在端侧」真正要防的是
> 「把服务端当作内容分发的主路径」，而**不是禁止服务端持有文字副本**。
> 实现 `/api/items/:id` 时才看清：全部正文合计仅约 120KB，且这些文字
> **早已以检索片段形式存在服务端**（RAG 必需），把它们拼回完整对象既不增加成本、
> 又让接口变得可用。真正属于端侧专属的是**图片二进制**。详见 ADR-024。

## ADR-011 工程命名与最低兼容版本

- **日期**：2026-09-29 ｜ **状态**：已采纳
- **背景**：包名后期改动成本高（连带签名配置与 AGC 注册），需一次定死
- **决策**：鸿蒙工程名 `YellowRiverArchive`，包名 `com.yellowriver.archive`，`compatibleSdkVersion` = 17
- **备选**：用队名或学校拼音命名；`compatibleSdkVersion` 设为 26（与 SDK 一致）
- **理由**：工程命名保持中性，不含校名与队名，符合提交材料的匿名要求；API 17 是工具链允许的下限，覆盖范围最广，避免现场演示设备版本过低装不上
- **影响**：代码只允许使用 API 17 可用的基础能力，不得使用新特性

## ADR-013 图片策略：主图必配 + 补充可选

- **日期**：2026-09-22 ｜ **状态**：已采纳
- **背景**：五层内容都要配图，全套 3-5 张/条将产生 240-400 张图，找图与版权核查工作量巨大
- **决策**：每条必须配 1 张主图（共 80 张），关键遗址再补 2-3 张（约 150 张）；统一 WebP、长边 ≤1080px、另出 200px 缩略图；主图由条目撰写人负责，补充图由 C 统一补
- **备选**：每条 3-5 张全套；或图片最少、靠自绘示意图
- **理由**：图片是安装包体积的唯一风险点（约 25-50MB），也是版权风险集中处；主图必配保证观感底线，补充图按资源情况弹性处理
- **影响**：预计总图量约 230 张，安装包控制在 30-55MB

## ADR-014 数据规模与城市分配

- **日期**：2026-09-22 ｜ **状态**：已采纳
- **背景**：赛题沿黄城市为三门峡 / 洛阳 / 郑州 / 开封 / 濮阳，但各市遗产资源量差别很大
- **决策**：共 80 条，不均等分配——洛阳 20 / 郑州 20 / 开封 16 / 三门峡 14 / 濮阳 10
- **备选**：五城均分 16 条
- **理由**：濮阳的国保单位数量有限，可用的地点型遗产约 8-10 处，强行凑到 16 条只能拉低质量；把差额补给资源更丰富的洛阳与郑州
- **影响**：`sites.yaml` 需按此配额校验各城条目数，缺口提前预警

## ADR-015 内容生产流程：AI 起草 + 人工改写

- **日期**：2026-09-22 ｜ **状态**：已采纳
- **背景**：80 条 × 五层内容约 15-20 万字，纯人工撰写周期过长；赛题严禁抄袭剽窃
- **决策**：六步流水线——人工来源摘录 → AI 起草（输出草稿，禁止直接入库）→ 人工改写 → 交叉校对（校对人与撰写人不得相同）→ 自动质检（含 n-gram 查重）→ 入库
- **备选**：纯人工撰写（慢）；直接由 AI 生成后入库（抄袭与事实风险高）
- **理由**：来源摘录让 AI 有据可依、改写有对照、`sources` 字段自动有据可填；人工改写负责去 AI 腔与事实核对；查重脚本以"与来源连续重合 ≤15 字"为红线
- **影响**：中间产物（`drafts/` 与 `sites/`）都是人可编辑的 YAML，便于 diff 与评审

## ADR-016 开发顺序：先端侧垂直切片

- **日期**：2026-09-30 ｜ **状态**：已采纳
- **背景**：端侧是评分主体，后端是加分项；数据工程是长尾工作
- **决策**：先做 P0 地基（仓库 + 契约 + 工程骨架 + 四个技术验证），再用 3-5 条手写数据跑通端侧"浏览 → 检索 → 详情"垂直切片，然后数据工程与后端并行推进
- **备选**：数据与后端先行，端侧后做
- **理由**：先用最小数据量验证环境、RDB、UI 框架与数据契约，避免契约错误导致两端返工；数据工程可以长尾并行，不应阻塞代码
- **影响**：P1 阶段只需 5 条数据，不要等 80 条写完才动手

## ADR-017 使用真机开发，不下模拟器镜像

- **日期**：2026-09-30 ｜ **状态**：已采纳
- **背景**：模拟器镜像需 30 分钟以上下载且占用磁盘；团队有 1 台华为真机
- **决策**：开发与调试以真机为主，不下载模拟器镜像
- **备选**：下载 phone 镜像（及 tablet 镜像作第二设备）
- **理由**：真机调试更贴近最终演示环境，且能验证分布式软总线（模拟器通常不支持）
- **影响**：UI 迭代依赖 `devecocli run --apply` 增量部署保证效率；**第二台设备的问题更突出**，需尽早落实借机或采购方案（见看板阻塞区 B1）

## ADR-018 协作方式

- **日期**：2026-09-22 ｜ **状态**：已采纳
- **背景**：三人协作，需要轻量但明确的协作规则
- **决策**：GitHub 私有仓；简化分支模型（`main` / `feat/*` / `fix/*` / `data/*`）；本地 `.githooks` 钩子（pre-commit 快检查、pre-push 重量检查），不启用 CI；任务与进度用仓库内 `docs/board.md` 看板
- **备选**：标准分支模型（含 dev 分支）；GitHub Actions；Issues + Projects

## ADR-019 共享契约必须写成 ArkTS 子集

- **日期**：2026-10-05 ｜ **状态**：已采纳
- **背景**：D0 阶段实测发现，把普通 TypeScript 声明文件原样生成为端侧 `.ets` 时，`devecocli check arkts` 报出 **42 个错误**，全部集中在 6 类语法上
- **决策**：`packages/shared` 中会被生成到端侧的四个文件（`constants` / `models` / `preset` / `api`）一律写成 **ArkTS 子集**；`tools/gen` 只做逐字复制 + 加头，不做语法转换
- **备选**：让生成器做 TS → ArkTS 的语法转换
- **理由**：转换器需要维护一张语法映射表，随两端语言演进而持续失效；写成子集则两端共用同一份源码，零转换、零漂移，且 `devecocli check arkts` 可直接当作契约的守门人
- **影响**：以下语法在整个共享契约中**禁用**：

| 禁用语法 | 报错规则 | 替代写法 |
|---|---|---|
| `as const` | `arkts-no-as-const` | 显式标注类型的数组：`const X: T[] = [...]` |
| `(typeof X)[number]` | `arkts-no-aliases-by-index` | 手写字符串字面量联合类型 |
| `typeof` 类型查询 | `arkts-no-type-query` | 同上 |
| 内联对象类型 `{ a: number }` | `arkts-no-obj-literals-as-types` | 声明具名 `interface` |
| 未标注类型的对象字面量 | `arkts-no-untyped-obj-literals` | 先声明 interface 再标注 |
| 数组展开 `[...a, b]` | `arkts-no-spread` | 逐项写全 |

- **额外收益**：手写的 ArkTS 代码（Index / 各页面 / 主题常量）在同一轮检查中**零错误**，说明子集约束一旦建立，端侧代码质量可被工具持续验证

## ADR-020 D0-V 四项技术验证结论

- **日期**：2026-10-05 ｜ **状态**：已采纳
- **背景**：D0 地基完成后，四个关键技术假设需要在真机上实测才能确定后续设计；服务器与端侧的性能预算都建立在这些假设上
- **测试设备**：华为畅享 90 Pro Max（API 26）
- **决策**：依据下列实测结果调整设计（见「影响」）

| 验证 | 测试内容 | 结果 |
|---|---|---|
| **D0V-1** 分布式键值库 | KVManager 创建、协作型存储打开、增/读/前缀遍历/删 | **通过**（首次 574ms，含初始化；后续 79ms；写 3 条 29ms） |
| **D0V-2** 关系型存储 | RDB 建表 + 批量写入 1000 条（每条约 250 字）+ 全表扫描 + 条件查询 | **通过**（批量写入 **50ms**，全表扫描 0ms，条件查询 2-3ms） |
| **D0V-4** 图片资源加载 | rawfile 串行读取 50 张 WebP（1080×720，单张 136KB，共 6.5MB） | **通过**（总耗 **11ms**） |
| **D0V-3** 力导向布局 | Canvas 绘制 200 节点 / 300 连边，含斥力+弹簧+向心+阻尼，连跑 60 帧 | **通过**（**6.57ms/帧**，折算 152fps） |

**影响**：

1. **首启导入不需要进度条或分片导入**。全量预计 80 条档案 + 约 1500 个 chunk，按实测速度约 100ms 完成
2. **图片尺寸策略维持不变**（WebP、长边 1080px、单张 80-150KB）。230 张图片读取约 100ms，不是瓶颈；体积预算的约束仍然是安装包大小而非性能
3. **图谱页可直接用朴素力导向，但仅在 200-300 节点范围内**。斥力是 O(n²)：200 节点 6.57ms/帧，推算 500 节点约需 35ms/帧（约 28fps），**届时必须启用网格桶近似**（与 设计文档 §7.3 一致）
4. **distributedKVStore 可用**，本地读写、前缀遍历、删除全部正常，耗时在毫秒级，完全能承载收藏/笔记/标签的写入量

**遗留**：真正的**跨设备同步**尚未验证——directional 同步需要第二台可信设备。当前只有一台真机，需借机或临时下载 tablet 模拟器镜像补验（见看板 B1）。通道 A 的代码可先按 API 文档实现，待第二台设备到位后一次验证。

## ADR-021 ArkTS 的 @Builder 只接静态标识，状态一律用 this 读

- **日期**：2026-10-05 ｜ **状态**：已采纳
- **背景**：D1 检索页的第一版把筛选状态当参数传进 `@Builder filterRow(title, values, selected, onToggle)`。实测表现：点击筛选 chip 后界面**不刷新**（选中态不变），且检索引擎收到的条件与界面显示不一致
- **决策**：`@Builder` 只接收**静态标识**（如 `'city'` / `'era'` / `'type'`），凡参与渲染的可变状态一律在 Builder 内部通过 `this.xxx` 直接读取
- **备选**：用 `$$` 双向绑定；或完全放弃 Builder、把 UI 内联到 `build()`
- **理由**：ArkTS 中 `@Builder` 的**值参数按值传递，不具备响应性**——参数变化不会触发 Builder 内 UI 刷新，而状态赋值是生效的，于是造成"数据变了但界面不变"的隐蔽不一致。通过 `this` 读取状态时，Builder 会随组件重渲染而重新执行
- **影响**：写进 [开发规范](./开发规范.md) §4.2，列为端侧编码硬规则；本次修复后筛选 chip 选中态与检索引擎条件恢复一致（已在模拟器上验证）
- **另一条并发约定**：异步检索必须在**调用点锁定**查询串与筛选条件（`const query = this.keyword`），再进入 await，避免 await 期间状态变化导致"结果与展示不符"

## ADR-022 数据核实改为「领域知识初稿 + 人工核对」双轨

- **日期**：2026-10-05 ｜ **状态**：已采纳
- **背景**：原计划由 Agent 联网核实 80 条清单的城市归属、年代、类型、文保级别与坐标。实测网络环境后否决了该路径
- **实测结果**：

| 源 | 可达性 | 可否抓取 |
|---|---|---|
| Wikidata SPARQL | 不可达 | — |
| 中文维基百科 | 不可达 | — |
| 百度百科 | 可达 | **需验证码**，不可抓取 |
| 中国大百科全书 | 可达 | JS 单页应用，内容不由 HTML 返回 |
| 国家文物局（不可移动文物信息） | 可达 | JS 动态渲染，名录链接均为 `javascript:;`，无可直接调用的接口 |

- **决策**：改为双轨制
  1. **Agent 侧**：基于领域知识产出带**置信度标注**的清单草稿（`sites.yaml`），仅对高置信项标 `已核`
  2. **人工侧**：队友用浏览器按 [数据规范](./data-spec.md) §8 的核对清单逐项确认
- **备选**：自行搭建维基镜像；用付费商业数据接口；只收录能自动核实的少量条目
- **理由**：前两者成本超出学生团队范围；后者会让 80 条规模目标落空。双轨制把机器能做好的（结构、一致性、分布校验）交给机器，把需要人判断的（事实核对）交给人，且**不假装置信**
- **影响**：`sites.yaml` 增加 `confidence`（high/medium/low）与 `status`（已核/待核/存疑）两个字段；置信度为 low 的条目**不得进入 P0 批次**（由 `pnpm data:sites` 自动拦截），且在核对完成前不写正文

## ADR-023 用 Node 内置的 node:sqlite 替代 better-sqlite3

- **日期**：2026-10-05 ｜ **状态**：已采纳
- **背景**：服务端需要 SQLite 存储（FTS5 关键词索引、向量、图谱表）。原计划用 `better-sqlite3`
- **决策**：改用 Node 内置的 `node:sqlite`（`DatabaseSync`）
- **备选**：`better-sqlite3`（原生模块，需编译或预编译二进制）；`sql.js`（WASM，性能差）；独立数据库进程
- **理由**：实测 Node 26 内置的 SQLite 为 **3.53.4**，且**编译时已启用 FTS5**（`CREATE VIRTUAL TABLE ... USING fts5` 与 `bm25()` 排序函数均可用）——正好是 BM25 检索需要的全部能力。内置模块意味着：无原生依赖、无构建审批、无 Node 版本升级后二进制不匹配的风险
- **影响**：
  - 依赖表里删掉 `better-sqlite3` 与 `@types/better-sqlite3`
  - 服务端与流水线统一使用 `node:sqlite` 的同步 API（`DatabaseSync`）
  - 需注意 **Node 版本要求提高到 22+**（`node:sqlite` 自 Node 22 引入），已在 `engines` 中声明 20+ 的旧约定同步上调
  - 服务器部署时无需任何编译工具链，`node + tsx` 即可跑起来

## ADR-024 修正 ADR-010 的边界：文字可在服务端，只有图片二进制是端侧专属

- **日期**：2026-10-05 ｜ **状态**：已采纳（修正 ADR-010）
- **背景**：实现 `/api/items/:id` 时发现，按 ADR-010 的字面解释「服务端不持有档案」，这个接口只能返回残缺对象。但实测全部 80 条正文合计仅约 **120KB**，且**这些文字早已以检索片段形式存在服务端**（RAG 必需）——为「不重复存文字」而返回半个对象，是形式主义
- **决策**：服务端导入完整条目文本（含 events/poems/artifacts 等结构化字段），`/api/items/:id` 返回标准 `HeritageItem`。**图片二进制不入库**，只存路径引用与授权描述符
- **备选**：只存检索切片，详情接口返回残缺对象并标 `missingFields`（已实现过一版，评估后放弃）
- **理由**：
  - 文字量小，重复存储无成本；图片才是体积问题（80 张 WebP 约 10-20MB）
  - 服务端持有完整文字，才能支撑带完整引用的 RAG 回答、Web 展示页
  - 契约保持 `ItemDetailResponse = HeritageItem`，端云两侧类型一致，无额外认知负担
  - 「为形式而残缺」的接口会立刻制造额外解释成本（客户端必须处理缺失分支），收益却是负的
- **影响**：
  - `items` 表改为「筛选列 + payload JSON」的存储方式，payload 即端侧要的 `HeritageItem` 形状
  - 列表接口只取轻量列，不拖正文
  - ADR-010 的表述收窄为：**图片二进制与端侧离线优先体验是端侧专属**；服务端不做内容分发主路径

## ADR-025 分词器下沉为 @yra/nlp 共享包，查询期以 vocab.json 为词典

- **日期**：2026-10-05 ｜ **状态**：已采纳
- **背景**：实现 BM25 检索时遇到一个必须解决的问题 —— **索引是按分词结果建的**，查询串若用不同方式切分，FTS5 不会报错，**只是搜不到结果**。而分词器原先在 `tools/pipeline/src/tokenize.ts`，app 不该依赖 tools 包
- **决策**：
  1. 分词器下沉为独立包 `@yra/nlp`，构建期与查询期共用
  2. 服务端**以预置包的 `vocab.json` 为查询期词典**，不读 `packages/data/lexicon.txt`
- **备选**：服务端依赖 `@yra/pipeline`（依赖方向反了）；查询期读 `lexicon.txt`（存在两份词典不同步的风险）
- **理由**：
  - 词典一致性是**静默失效**类问题，必须从结构上消除而非靠约定维护
  - `vocab.json` 由同一次分词产出，天然与索引一致；`lexicon.txt` 只是建词典的**输入之一**，缺少从数据自动抽取的专名（遗址名、文物名、人物名）
- **验证方式**：下沉后重跑 `pnpm data:build`，所有依赖分词的产物**逐字节一致**（chunks / vocab / items / graph / similar 的哈希全部未变，仅 meta.json 的时间戳变化）——这是重构无副作用的确证
- **影响**：`tools/pipeline/src/tokenize.ts` 变为转出；`@node-rs/jieba` 依赖从 pipeline 移到 nlp；服务端新增 `@yra/nlp` 依赖

## ADR-026 双通道检索用 RRF 融合，单通道保留原始分数

- **日期**：2026-10-05 ｜ **状态**：已采纳
- **背景**：关键词通道（BM25，无上界）与语义通道（余弦，[-1,1]）的分数**量纲不可比**，需要定融合方式
- **决策**：
  1. 两通道都有结果时用 **RRF**（k=60）融合排名位次，不对分数做标定
  2. 只有单通道有结果时**直接用该通道的原始分数**，不强制走 RRF
- **备选**：加权求和（需拍一个没有依据的权重系数）；单一通道（放弃语义召回或精确匹配）
- **理由**：
  - RRF 只依赖排名位次，**不需要标定**。加权求和必须回答「BM25 的 8.5 分相当于余弦的多少分」——这个问题没有客观答案，拍出来的系数在数据分布变化后会失效
  - 单通道时保留原始分数，是因为分数量级本身有诊断价值：`cos=0.40` 说明「中等相似」，而 RRF 化后会变成 `0.0164`，看不出强弱
  - 实测验证：语义召回场景（查询「佛教石刻造像」而库中无石窟寺条目）只有语义通道有结果，返回 `cos=0.4031` —— 这个值明确告诉调用方「有中等相似的内容」，比一个恒定的 RRF 分数有用
- **代价**：`score` 的量纲随通道数变化。已在契约里明确「**只在同一次响应内可比**，排序可信、数值仅供参考」——这与 Elasticsearch 的 `_score` 约定一致
- **影响**：客户端不得基于绝对分数做阈值判断；如需「是否有相关结果」的判断，应依据 `hits.length` 与 `degraded`

### 附：实测效果（D3-10 完成时）

| 验证项 | 结果 |
|---|---|
| T-1（BM25 短文档偏置） | **已解决**。「绿松石龙形器」查询下 `archaeology`（0.0488）超过 `travel`（0.0246），而纯 BM25 时 travel 反超 |
| 语义召回 | 「早期国家的都城」「瓷器烧造中心」等关键词零命中的表述均能召回正确条目 |
| 查询嵌入缓存 | 二次查询 202ms → 2ms |
| 筛选穿透 | 城市筛选在两条通道上均生效（限洛阳→二里头、限濮阳→西水坡） |
| 降级路径 | 密钥失效时 `degraded=true`、`channels=['keyword']`，检索照常返回结果 |

## ADR-027 精排为可选且失败不致命；用量以 provider 累计值取差记账

- **日期**：2026-10-05 ｜ **状态**：已采纳
- **背景**：检索链最后一步要接 Rerank（交叉编码器精排），同时需要让外部调用成本可观测
- **决策**：
  1. 精排通过请求级开关 `rerank`（默认开启）控制，**客户端可关**
  2. 精排失败（超时/限流/欠费）**不视为错误**，静默退回融合顺序，响应不含 `reranked` 字段
  3. 用量记账不改动 provider 接口，以「调用前后读累计 token 取差值」实现
- **备选**：精排无开关（客户端失去控制）；精排失败时让请求失败；给每个 provider 方法加返回值带用量
- **理由**：
  - **客户端需要开关**：边输入边搜（搜索建议）场景下每次按键都精排既慢又费钱；应由客户端在「用户停下输入」时才开启
  - **失败不致命**是路演保命设计的延续：精排是锦上添花，网络抖动不该让整个搜索挂掉。为了不误报故障，「是否精排成功」用**正字段**表达（有 `reranked: true` 才算成功），而不是 `rerankFailed: false` 这种需要判断缺失值的写法
  - **取差记账**避免了改动 provider 接口（他们只暴露累计值），也让缓存命中可以记成 0 token 的独立操作，从而看清缓存究竟省了多少次
- **影响**：`usage_log` 表记录 operation / tokens / elapsed_ms / ok；`/api/stats/usage?days=N` 汇总
- **实测**：单次查询约 6-350 token；5 次查询合计 1775 token，其中精排 1744、嵌入 31 —— **精排是成本大头，嵌入很小**

 ├─ 语义通道：嵌入（LRU 缓存）→ 点积 top(3×K)

## ADR-028 同步记录 id 由目标确定性生成；软删墓碑；待推送集由时间戳推导

- **日期**：2026-10-06 ｜ **状态**：已采纳
- **背景**：实现个人数据（收藏/笔记/标签/主题/已读）的跨设备同步，需要定下三条影响收敛正确性的数据约定
- **决策**：
  1. **收藏与已读的 id 由目标确定性生成**（`site:ly-erlitou`），笔记与主题用随机 id
  2. **删除一律软删**（`deleted=1`），保留墓碑
  3. **待推送集由 `updated_at > lastPushedAt` 推导**，不建队列表
- **理由**：
  - **确定性 id**：两台设备各自收藏同一条目时，若 id 随机会产生两条记录，LWW 只能比较它们各自的时间戳，**无从收敛成一条**，用户会看到重复项。用目标派生 id 则两条记录天然是同一个键，后写者覆盖即可。笔记相反 —— 同一目标允许多条，被合并才是错误
  - **软删墓碑**：硬删后，对端推送的旧版本会把记录"复活"。这是分布式同步最常见的坑，且表现为"偶发数据回来了"，极难复现
  - **时间戳推导**：队列表必须与数据表保持同步，漏更新就会出现"永远推不完"或"改了没推"的隐形 bug。时间戳推导是自在自为的，不会与数据脱节
- **影响**：所有可同步表必带 `updated_at / created_at / device_id / deleted` 四列

### 附一：LWW 兜底规则必须两端对称

时间戳相同时（两端在同一毫秒各自修改）用 `deviceId` 字典序兜底。**关键是这条规则必须确定性且两端一致** ——
若一端判"本地赢"、另一端判"远端赢"，两台设备会永久分叉，且每次同步都各自再改一遍，永远收敛不了。
自检里专门验证了"两个方向判定相反"（`remoteWins(a,b) && !remoteWins(a,b)` 的反向）。

### 附二：两个实测踩到的坑

| 坑 | 现象 | 原因与修正 |
|---|---|---|
| `store.sync([])` | 报 `params deviceIdList must be array` | API 26 下空数组**不再表示**"广播给所有设备"，必须先从 `distributedDeviceManager.getAvailableDeviceListSync()` 取 `networkId` 列表再传入 |
| `entry.value` 读取为空 | 前缀扫描返回 0 条，**不报错** | SDK 里 `Value` 是**接口**（`{type, value}`），而 `store.get()` 返回裸联合类型，两者不能互相赋值。按裸类型读 `entry.value` 时 `typeof` 判不出字符串，静默返回空串 |

第二个坑尤其值得记：**类型不符却没有异常，只是数据读不到**。若没有把"单键直读"与"前缀扫描"分开验证，这个问题会被误判成"分布式 KV 不能用"而错误地放弃主通道。

## ADR-029 同步游标用服务器单调序号；服务端持权威版本；广播不推进游标

- **日期**：2026-10-06 ｜ **状态**：已采纳
- **背景**：实现服务端同步通道（WS），需要定下三件影响协议正确性的事
- **决策**：
  1. 拉取游标用 `sync_changelog.seq`（自增单调序号），**不用时间戳**
  2. 服务端保存**权威版本**，所有设备推拉都经它裁决，不做设备间两两同步
  3. 实时广播**不推进**客户端游标，游标只由显式 pull 推进
- **理由**：
  - **不用时间戳游标**：若客户端游标是 T、而一条新变更的服务器时间戳恰好也是 T，下次拉取用 `> T` 会把它**永久漏掉**。同毫秒内产生多条变更时尤其容易触发。单调序号只在有变更时递增且严格可比较，没有这个窗口
  - **服务端持权威版本**：若让设备两两同步，三台设备时的收敛轮数随设备数平方增长，且「谁最终赢」依赖同步顺序 —— 结果是不可预测的。由单一权威裁决则每次同步都是一次收敛
  - **广播不推进游标**：广播是尽力而为的优化（对端可能离线、消息可能丢）。若用广播推进游标，丢一次广播就永久漏掉那批变更。代价是广播过的变更会在下次 pull 时重复下发 —— 但 LWW 下重复应用是幂等的，**用冗余换正确性**
- **影响**：`SyncPull.since` 与 `SyncPulled.cursor` 都是序号；`serverTime` 仅供展示

### 附一：LWW 的第二实现是刻意的

端侧 `PersonalDao.applyRemote` 与服务端 `applyPush` 是同一套 LWW 规则的两份**独立实现**。
这不是冗余 —— 两份实现互为参照：若对协议的理解有偏差，两端行为会出现分歧，
比单份实现更容易暴露问题。

### 附二：双设备协议验证（模拟设备，17/17 通过）

用两个 Node 客户端代替两台真机，因为**云端通道是设备无关的** ——
它只认 `userId + deviceId`，不关心对端是鸿蒙设备还是 Node 进程。
因此协议正确性可完整验证，不需要第二台物理设备。

`pnpm sync:test`（需先启动服务）：

| 组 | 验证项 |
|---|---|
| 身份绑定 | 配对码生成、双设备绑定同一 userId、**配对码一次性（重放被拒）** |
| 建连 | 两端收到初始 state 帧（含服务器游标） |
| 推送/拉取 | 推送被接受、对端**实时广播**收到、**推送端不收回声** |
| 游标语义 | 无变更返回空、新变更可拉到、重复拉取为空（严格单调） |
| LWW 裁决 | 旧版本被拒（服务端保持权威）、新版本被接受 |
| 同时间戳兜底 | **deviceId 大者胜且反向被拒**（规则可交换，防永久分叉） |
| 软删 | 以墓碑形式传播，而非记录消失 |
| 冲突与设备 | 冲突记入服务端日志、两台设备已登记 |

**这解决了看板 B1 的协议层面**。剩余部分（分布式软总线真机对真机）属于通道 A，仍需第二台设备。

### 附三：实现中踩到的两个坑

| 坑 | 现象 | 原因 |
|---|---|---|
| `AS table` | 推送报 `near "table": syntax error` | **`table` 是 SQLite 保留字**，不能作列别名。改用 `AS tableName` |
| `logConflict` 缺 user_id | 冲突写入了但按 userId 查永远是 0 条 | INSERT 没写 `user_id`，落库时用了列默认值 `''`。**没有报错**，只是数据去了另一个"用户"名下 |

第二个坑又一次印证同一个模式：**数据写错了地方而不报错**，比抛异常难查得多。

## ADR-030 推送游标推进到「已推送记录的最大时间戳」，不用 now()

- **日期**：2026-10-06 ｜ **状态**：已采纳
- **背景**：端侧 CloudSync（D4-7）接入后，用两台模拟器做端到端验证时发现：手机明明有收藏，「立即同步」却报告**推送 0 条**，且服务端记录数一直是 0，**没有任何报错**
- **决策**：推送游标 `lastPushedAt` 推进到**本轮实际推送成功的记录里最大的 `updatedAt`**，且仅在本轮确有推送时推进
- **备选**：用 `now()` 作游标（最初实现，错误）
- **理由**：用 `now()` 是分布式同步的经典错误。同步是个有耗时的过程：在这期间写入的记录，其 `updatedAt` 必然**小于** `now()`，游标一旦前进到 `now()`，这些记录**永远推不上去了**；同理，本轮推送失败的记录也会被永久跳过。用「已推送内容的最大时间戳」作游标，未推送的记录下次仍会被捞到，语义上也不会跳过任何东西
- **代价与补救**：历史上被错误推进的游标值已经存进设备库，仅改代码无法自愈。因此补了一个**「重置游标」**操作（同步中心页可见）—— 这类「同步卡住但无报错」的情况真实存在，给用户留一个出口比让数据永远出不去要好

### 附一：通道选择判据的修正

原逻辑用「pull 是否拉到数据」推断通道 A（分布式软总线）是否有对端。**这个判据是错的** ——
本地残留（自检写入的探针、上一轮自己推上去的记录）同样会让 pull 非空，
于是被误判成「有对端」，**云端兜底通道永远不会启用**。

改为用 `syncComplete` 回调给出的**对端数量**判断（`hasPeers()`），这是唯一可靠的来源。

### 附二：两模拟器端到端验证（成功）

此前 B1 只验证到协议层（两个 Node 客户端）。本次用**两台真实模拟器跑同一份 App** 验证了完整链路：

| 设备 | 角色 | 操作与结果 |
|---|---|---|
| Pura 90 Pro（手机） | 生成配对码方 | 生成 6 位码 → 另一台输入加入 |
| Mate X7（折叠屏） | 输入配对码方 | 输入码 → 「配对成功」，两端 userId 一致 |
| 手机 | 推送端 | 同步 → **推送 3 条**（收藏/笔记/已读），服务端 `records=3` |
| 折叠屏 | 拉取端 | 同步 → **拉取 3 条、应用 3 条**，收藏 **0 → 1** |

**B1 至此完成**：协议层与端到端链路均已验证。剩余未验证的只有通道 A 的「分布式软总线真机对真机」，
它需要同华为账号 + 超级终端信任环，模拟器无法组建。

### 附三：操作层面的坑

`devecocli ui click` 的点击在**软键盘展开时会被吞掉**（用于收起键盘），表现为「按钮点了没反应」。

再取一次布局坐标后点击 —— 键盘开关会改变下方元素位置。

## ADR-031 推送游标与拉取游标必须分开存，且量纲不同

- **日期**：2026-10-06 ｜ **状态**：已采纳
- **背景**：D4-11 补验时发现，设备首次同步之后**再也拉不到任何服务端变更**，且不报错
- **决策**：两个游标分开存、语义各自明确：
  - `lastPushedAt` —— **本机记录时间戳**（约 1.79e12），用于「哪些本地改动还没推上去」
  - `lastPulledAt` —— **服务端自增序号**（1、2、3…），只能由服务端返回值推进
- **错误做法**：用同一个 `lastPushedAt` 兼作拉取游标
- **理由**：两者**量级差 12 个数量级**。把时间戳当序号传给服务端，`seq > 1.79e12` 恒为空 ——
  首次同步之前游标是 0，恰好能拉到全部数据，所以**首次是正常的**；一旦同步过一次，
  游标被写成时间戳，此后永远拉空。这个 bug 的形状很坏：**首次成功、之后静默失效**
- **影响**：
  - `pull()` 传入 `lastPulledAt`，并用 `SyncPulled.cursor`（服务端回的序号）推进它
  - **不得**用本机 `now()` 覆盖 `lastPulledAt`
  - 「重置游标」两个都要清

### 附：D4-11 补验完成（绕开 UI 的方法）

**冲突列表的展示格式已验证**：`table · recordId`、采用方（本机/远端）、双方时间戳。

### 附二：自检覆盖冲突列表导致真实冲突被挤出

自检的清理用 `record_id LIKE 'selftest%'` 匹配冲突表，但 `record_id` 的实际形状是
**带目标类型前缀**的 `site:selftest-item`，模式匹配不上 —— 于是每次自检都在冲突列表里
堆一条，实测中 5 条里 4 条是自检残留，把真实冲突挤出了可视范围（列表只显示最近 5 条）。
已改为 `%selftest%` 包含匹配，并在清理时一并清掉分布式 KV 里的探针。

## ADR-032 备份恢复走与同步相同的 LWW 合并路径，不直接覆盖

- **日期**：2026-10-06 ｜ **状态**：已采纳
- **背景**：实现 D4-10 备份恢复，需要决定「导入/恢复」如何与既有数据合流
- **决策**：
  1. 备份载荷**导出完整记录**（含 `updatedAt` / `deviceId` / `deleted` 三个 LWW 元数据），不是「当前有效数据」
  2. 导入与恢复都**转成 ChangeSet 后复用 `applyRemote`**，不另写合并逻辑
  3. 云端快照**不直接改服务端数据**，而是作为一批「远端变更」返回给客户端合并
- **理由**：
  - **导出的必须含元数据**：少了它，导入时无从判断该保留哪一份，只能整份覆盖 ——
    那会悄悄丢掉导入之后产生的更新
  - **复用 applyRemote**：让「导入」「同步」「快照恢复」三条路径的行为天然一致。
    如果各写一套，必然出现「导入会覆盖、恢复不会」这类让人记不住、也测不全的差异
  - **恢复不覆盖**：用户点「恢复」通常想的是「把丢掉的东西找回来」，
    而不是「把状态回退到那一刻、丢掉之后所有改动」。按 LWW 合并能同时满足两者 ——
    快照里独有的记录会补回来，快照之后的新改动会保留
- **代价**：无法实现「精确回退到某一时刻」。若将来需要该语义，应另做一个显式的
  「强制回滚」操作（并在 UI 上明确警示），而不是改变「恢复」的默认行为

### 附：实测结果（手机 Pura 90 Pro）

| 操作 | 结果 |
|---|---|
| 导出备份 | `已导出到 yra-backup.json（1 KB）` |
| 存云端快照 | `快照已保存：3 条记录 / 1 KB`（服务端 `count=1`，778 字节） |
| 从快照恢复 | `已按最新时间戳合并：应用 0 条、保留本地 3 条、冲突 0 条` |
| 导入恢复 | `导入完成：应用 0 条、保留本地 2 条、冲突 0 条` |

后两项的「应用 0 条、保留本地 N 条」**正是设计意图的体现** ——
所有记录版本相同，被 `isSameVersion` 正确跳过，证明合并是幂等的、
恢复不会无谓地覆盖本地。

## ADR-033 引用区只回传「回答里真正引用到的资料」

- **日期**：2026-10-06 ｜ **状态**：已采纳
- **背景**：问答链路初版把送进模型的 6 条资料**全部**作为引用回传
- **决策**：从回答文本里解析 `[n]` 标记，只回传被引用到的资料，并**重新编号**；解析不到编号则不回传引用
- **备选**：全部回传（初版做法）；用相关性阈值筛
- **理由**：
  - 引用区的价值在于**「每条结论都可核查」**，不在于条目多。送进模型 6 条、
    回答只用到 2 条时，另外 4 条是噪声 —— 用户会以为它们支撑了结论，点进去却发现无关
  - **不用阈值筛**：阈值需要标定（「0.31 算相关吗？」没有客观答案），且回答质量由模型
    判断更准。让模型自己说它用了哪几条，是更直接的信号
  - **解析不到就返回空**：「档案中暂无相关记载」这类回答本就没有引用，此时列出资料是误导
- **影响**：`parseCitedIndexes()` 见 `apps/server/src/qa/service.ts`

## ADR-034 问答端侧页面的状态刷新问题（已解决）

- **日期**：2026-10-06 ｜ **状态**：**已解决**
- **背景**：D5-3 服务端问答链路已验证可用，但端侧 `AssistantPage` 的流式渲染未跑通

### 已确认的事实（缩小了排查范围）

| 环节 | 状态 | 证据 |
|---|---|---|
| 服务端问答链路 | ✅ **完全正常** | Node 客户端实测：检索 6 片段 → 流式 108 字 / 81 个 delta → done 带 3 条引用、`degraded=false` |
| 端侧 WS 建连 | ✅ 正常 | 设备日志：`连接中：ws://10.60.228.176:8787` → `已连接，准备发送` |
| 端侧发送 ask | ✅ 正常 | 设备日志：`发送结果=true`；服务端 `[qa]` 计数随之增长 |
| 服务端处理提问 | ✅ 正常 | 服务端日志：`[qa] 检索到 6 个片段，准备生成` → `[qa] 流式结束，累计 108 字` |
| **端侧接收与渲染** | ❌ **卡在 `正在检索档案…`** | 界面始终停在 pending 态，既不显示回答也不显示错误 |

**结论：故障边界在「端侧收到 delta 之后到界面刷新」这一段**，不在网络、不在服务端。

### 已尝试且无效的修法

1. **`@Observed` 模型类**：把 `QaTurn` 从普通 interface 改为 `@Observed class`，
   让外部服务直接改字段（原先是整体替换数组元素）。**无效**。
2. **按 ADR-021 改为从 `this` 读状态**：把 `@Builder answerBlock(turn: QaTurn)`
   改为 `answerBlock(index: number)`，内部读 `this.turns[index]`。
   理由是 ADR-021 已记录「@Builder 按值传参无响应性」。**无效**。

### 下一步的排查方向（给接手者）

按可能性排序：

1. **`socket.on('message')` 的第二个参数类型**。HarmonyOS 的 webSocket
   可能把文本帧以 `ArrayBuffer` 交付，而当前代码有 `if (typeof value !== 'string') return`
   的早退分支 —— 这会让所有消息被静默丢弃且不留痕迹。
   **验证方法**：在早退分支里打一条 hilog，看是否命中。
   *（注：CloudSync 用了同样的判断且工作正常，所以这条可能性中等）*
2. **`ForEach` 的 index 参数**。ArkUI 的 `ForEach` 第二个回调参数是否真为下标，
   各版本行为不一致。可改为在 `QaTurn` 上存一个自增序号字段，不依赖 ForEach 传 index。
3. **`@Builder` 内读 `this.turns[index]` 的追踪粒度**。ArkUI 可能只追踪
   `this.turns` 数组本身的增删，不追踪元素内部字段变化。此时需要改用
   `@ObjectLink` + 子组件（ArkUI 观察 `@Observed` 对象的标准做法）。

### 一条经验

本次调试中，**服务端与客户端各自都有日志、但两边的日志拼不出完整链路** ——
服务端只说「我发了 81 个 delta」，客户端只说「我收到了连接成功」。
缺的是**客户端消息到达的日志**。若一开始就在 `on('message')` 入口打一条日志，
本可以在 10 分钟内定位到「消息是否到达」这一层，而不是先花时间怀疑
`@Observed`、`@Builder` 这些渲染层的原因。

**教训：跨进程/跨网络的链路调试，第一件事是在每一跳的入口打日志，
先确定"消息到没到"，再讨论"为什么没渲染"。**

## ADR-034 附二：问题已解决 —— 顶层 @State + 静态缓冲轮询

### 最终采用的方案

`QaClient` 把流式结果写进一个**静态缓冲** `QaBus`，页面用 `setInterval(150ms)`
把它搬进**顶层的 `@State` 字段**。顶层赋值是 ArkUI 一定能观察到的。

### 为什么绕这一圈

ArkUI 对**嵌套状态**的观察粒度不如预期。实测把所有增量写进页面持有的对象字段
（普通 interface / `@Observed` 类 / `@ObjectLink` 子组件 / `@Builder` 读 `this`）
都没能触发重渲染，而消息本身是到达的（设备日志可见 126 条 `on message`）。

这个方案不好看（多一个静态字段与一次轮询），但**行为确定**。
在一个「不确定能不能刷新」的优雅写法和一个「一定能刷新」的朴素写法之间，选了后者。

### 排查过程中的两个教训

**一、先确定「消息到没到」，再讨论「为什么没渲染」。**
本次的服务端日志说「我发了 81 个 delta」，客户端说「连接成功」，
中间缺的恰恰是消息到达的日志。补上 `on('message')` 入口日志后，
一个问题就定位到了「传输正常、渲染有问题」这一层。此前先怀疑渲染层，
绕了远路。

**二、不要过早下结论。**
最后一次判定「仍然卡住」是**截图太早**造成的 —— 完整问答要 18-25 秒
（检索 + 精排 + 流式生成），而我在 18 秒时截图，看到 pending 就判断失败。
补上「`tick bus=168 state=166`」这类日志后才看清：机制一直是好的。

**教训：异步链路的验证，要么等到明确的完成信号，要么打点观察进展，
不要用「某一个时刻的画面」判断成败。**

## ADR-035 社区发现只在「语义骨架边」上跑，条目间要有关系边

- **日期**：2026-10-06 ｜ **状态**：已采纳
- **背景**：D5-1 社区发现（自动文化主题聚合）首次跑出来的结果是「每个条目自成一个社区」——
  5 条数据得到 5 个 12 节点左右的社区，等于没做聚合
- **决策**：
  1. 图构建时**增加条目间关系边**：`culturalLink`（由嵌入相似度）与 `nearby`（同城且 30km 内）
  2. 社区发现**只在语义骨架边上跑**（`locatedIn` / `belongsToEra` / `hasType` / `culturalLink` / `nearby`），
     排除叶子边（`unearthed` / `occurredEvent` / `hasPoem` / `collectedAt` / `relatedFigure`）
- **理由**：
  - **没有条目间边，图是 N 个互不相连的星形**，标签传播只能得到平凡解
  - **有边但保留叶子边，仍然聚不起来**：中心节点被自己的一堆「只连它一个」的卫星节点投票，
    跨条目的那条弱关系边根本投不过。这是本次踩到的第二个更隐蔽的坑 ——
    加了边却没效果，容易误判成「算法不对」
  - 只留骨架边后，同属仰韶的两个遗址经共享的「仰韶」节点天然连通，
    聚合结果才符合「文化主题」的语义
- **影响**：
  - `tools/pipeline/src/graph.ts` 增加两类条目间边；相似度是对称的，**必须去重方向**
    （否则可视化出现重叠边、度数翻倍，进而影响 PageRank 与社区发现）
  - `apps/server/src/graph/algorithms.ts` 增加 `SEMANTIC_RELATIONS` 与 `coreGraph()`
  - 社区名取「成员里 PageRank 最高的**实体**节点」——城市/时代/类型是抽象节点，
    拿「仰韶」当社区名不如拿「仰韶村遗址」，后者用户能点进去

### 实测

| 端点 | 结果 |
|---|---|
| `/api/graph/communities` | 西水坡遗址 **7 节点**（西水坡 + 濮阳 + 仰韶 + 聚落遗址 + 仰韶村遗址 + 三门峡…）、开宝寺塔/二里头/巩义窑址各 4 节点 |
| `/api/graph/path?from=sms-yangshao&to=py-xishuipo` | 三条路径：直连 / 经「仰韶」/ 经「聚落遗址」 |
| `/api/graph/ranks` | PageRank Top5：开宝寺塔 0.0802、巩义窑址 0.0790、二里头 0.0767… |

**跨城市的两个仰韶遗址被自动聚到一起**，是「自动主题聚合」这一创新点真正生效的证据。
（5 条样例只有一对相似度过阈值；80 条真实数据会有更多条目间边，聚合效果更明显。）

## ADR-036 图谱动画直接重绘 Canvas，不走 @State

- **日期**：2026-10-06 ｜ **状态**：已采纳
- **背景**：图谱页要做力导向动画（约 60fps）
- **决策**：动画循环里直接调 `ctx` 绘制，**不把节点位置放进 @State**
- **备选**：把节点位置放进 @State，让 ArkUI 负责重绘
- **理由**：60fps 意味着每秒 60 次状态更新，ArkUI 的 diff 与组件重建会成为瓶颈，
  而 Canvas 只是把像素画上去。**凡是"每帧都变"的数据都不该进状态系统** ——
  状态系统服务于"偶尔变、需要局部更新"的场景，用它驱动逐帧动画是用错工具
- **代价**：绘制与数据分离，交互时要手动调 `draw()`（例如点击选中后重绘一次）。
  这个代价是显式的、局部的，比"每帧 diff 整棵树"小得多

### 附：实测与两处实现细节

| 项 | 结果 |
|---|---|
| 渲染 | 57 节点 / 59 连边，类型着色 + 权重定大小 + 邻域高亮全部正常 |
| 性能 | D0-V 已验证 200 节点 6.57ms/帧；本页 57 节点余量充足 |

两个值得记的实现细节：

1. **布局尺寸必须在 `onReady` 时取真实画布尺寸**。最初硬编码 340×560，
   而实际画布更大，结果布局在一个比画布小的盒子里收敛，四周留一大片空白。
   修法是 `onReady` 时按 `ctx.width/height` 重建布局并重新撒点。
2. **初始位置用黄金角螺旋而不是随机撒点**。随机撒点初始能量高、布局抖动明显，
   且每次打开页面形态都不同；螺旋分布既均匀又确定性，观感稳定。
3. **收敛后停止迭代只保留重绘**（`energy() < 0.6`）。省电，也让画面不再微抖。

## ADR-037 断网时端侧检索兜底，而不是只报错

- **日期**：2026-10-06 ｜ **状态**：已采纳
- **背景**：D5-5 验证四级降级链时发现一个**实质缺口** —— 端侧问答页只调服务端，
  连不上就直接显示「无法连接问答服务，请检查网络后重试」。设计文档 6.2 要求的
  「完全断网 → 端侧 token 匹配检索」**并没有实现**
- **决策**：云端问答失败时，自动转端侧检索（`SearchService`，走预置包 + RDB，完全离线），
  把 Top-3 原文摘要作为回答展示，并明确标注「云端助手当前不可用」
- **理由**：
  - 这是**路演保命设计**。演示现场一旦网络出问题，问答页只剩一句报错，
    而这恰好是评委最可能点开的功能
  - 端侧检索本就已经实现（D1 的垂直切片），只是没有接到问答页上 ——
    属于「能力已有但没接线」，改造成本极低
  - **如实说明降级**：不假装是 AI 生成的答案，避免让用户误以为系统具备离线推理能力
- **影响**：`AssistantPage.localFallback()`；分区键需经 `SECTION_LABELS` 转中文
  （端侧检索返回的是 `archaeology` 这类键，直接展示会露出英文）
